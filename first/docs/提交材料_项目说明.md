## 0. 一分钟版

**做什么：** 用户把关注的观点类内容收进「仓库」；系统自动建一个「**反仓库**」，装那些他**没看见、但值得看见**的另一面 —— 同一场争论里的真实文章，带可验证出处，同样省流。

**凭什么不同：** 现在的推荐都在回答「你还想要什么」，没有人回答「**你漏了什么**」。

**怎么保证不编：** LLM 只负责「提出问题」（这段文本站在哪一边），**答案必须来自真实检索**；反库每一条都有可点开的 URL，以及从原文中截取的证据片段 —— 证据必须是原文的真实子串，对不上就丢弃。

**现在做到哪：** 一个 9 条的模拟库跑完，产出 6 条反库条目，全部带真实 URL，AI 自编 0 条；184 个检索候选被压到 6 条，其余每一条都记了「为什么不要」。

## 1. 项目简介

### 1.1 问题

今天的信息产品都在做同一件事：**把你想看的推给你**。你关注微服务，它就一直给你微服务；你相信 TDD，它就一直给你 TDD 的成功案例。

结果是每个人的信息视野越用越窄，而且**没有人负责告诉他："这件事还有另一面。"**

### 1.2 我们的答案

一个和「仓库」对称的东西：**反仓库**。

| 仓库（Vault） | 反仓库（Antipode） |
|---|---|
| 你说要什么，它去各个源里筛 | 它专门去找**与这些内容相对立**的观点 |
| 让你**读得完** | 让你**看得见盲区** |
| 排序：契合度 × 时间 | 排序：对立度 × 论证质量 |
| 存"我认同的" | 存"我该知道的" |

### 1.3 和"给我推点反对意见"有什么不一样

这是本项目最核心的设计判断：**「相反」不是一种东西，是三种。**

| 类型 | 定义 | 例子 | 本期状态 |
|---|---|---|---|
| **A 观点对立** | 同议题、反立场 | 你信微服务 → 找到"我们把微服务拆回单体" | ✅ 已实现并跑通 |
| **B 反向证据** | 反驳你结论的具体事实 | 你信"微服务=高可用" → 找到"某公司因微服务故障 12 小时" | 数据模型已留位 |
| **C 视野缺失** | 你完全没覆盖的相邻议题 | 你只看微服务 → 提示 Serverless | 数据模型已留位 |

不区分这三类，反仓库必然退化成"杠精池"。本期把 A 类做到可演示、可解释、可复现。

### 1.4 三条产品原则

1. **反推荐是可选开关，按库开启** —— 邮件、代码 issue 这类私人事务 / 工作材料本就没有"对立面"，不该开；只有观点类文章才开。
2. **反库物理独立** —— 不与仓库条目混放，靠 `for_vault_item` 一一对应。卖点就是"仓库之外还有一层"。
3. **没有反信息 ≠ 失败** —— 每条条目只有有限的几种归宿，每种都能解释。宁可空着，也不凑数。

## 3. 功能说明

### 3.1 用户看到的功能

| 功能 | 说明 | 现场可验证 |
|---|---|---|
| 双栏视图 | 左「仓库」是你收的，右「反仓库」是系统补的，一一对应 | `first/docs/反库演示.html` |
| 一键开关 | 反推荐可按库开关；关掉后右栏整体置灰 | 演示页右上角开关 |
| 回现场 | 每条反库条目点开即到原帖，正文里高亮出证据片段 | 演示页「回现场 ↗」 |
| 省流 | 每条只给一句"它到底在说什么"+ 立场标签 + 对立度 | 演示页卡片 |
| 没有就不给 | 找不到对立面时，明确写出原因（中立 / 议题不在表内 / 候选全被拒…） | 演示页灰底卡片 |
| 只给链接也能跑 | 队友只传 URL 时，系统自己取正文 | `first/data/vault_url_only.json` |

### 3.2 系统能力（模块）

| 模块 | 文件 | 输入 → 输出 | 状态 |
|---|---|---|---|
| ⓪ 取正文 | `vault_fetch.py` | URL → 标题 / 正文 / 站点 | ✅ 三层策略（站点适配 → 通用容器 → 分块打分） |
| 0 立场抽取 | `stance_extractor.py` | 文本 + 16 议题 → 立场 / 证据 / 置信度 | ✅ 四分类准确率 90.2% |
| 1 检索 | `antipode_sources.py` | 议题 + 反方 → 候选列表 | ✅ V2EX（sov2ex）/ 掘金 / CSDN / GitHub / HN |
| 2 粗筛 | `passage_selector.py` | 长文 → 作者真的在表态的段落 | ✅ 压缩比 36% |
| 3 判定 | `antipode_engine.py` | 段落 → 是否反方 / 对立度 | ✅ 含纠偏重判 |
| 4 闸门 | `antipode_engine.py` | 候选 → 采纳 / 拒因 | ✅ 六道 |
| 5 省流 | `antipode_engine.py` | 长文 → 一句话 | ✅ 附证据片段 |
| 6 入库 | `run_vault.py` | 库 → 反库 JSONL + 体检报告 | ✅ 断点续跑、九种归宿 |
| 7 HTTP | `server.py` | `POST /antipode` → JSON | ✅ 零依赖、仅本机监听 |
| 8 看板 | `make_defense_page.py` | 实测产物 → 答辩看板 | ✅ 数字不手抄 |
| 9 演示页 | `make_demo_page.py` | 库 + 反库 → 单文件 HTML | ✅ 断网可用 |

### 3.3 两条铁律（实现层面的硬约束）

1. **LLM 只负责"提出问题"，答案必须来自真实检索。** 引擎里没有任何一条路径允许模型"写出"一篇反方文章。
2. **对立面 = 符号运算。** `takes_side == opposite(原条目.supports)`，没有"大致相反"。这条使得整个判定可以被单测覆盖，而不是靠模型"感觉"。

### 3.4 防"杠精化"的六道闸门

| 闸门 | 拦什么 | 例子 |
|---|---|---|
| ① 对立性表述 | 正文里没有真正表态 | 只是提问、只是转载 |
| ② 对立度阈值 | "有点不一样"不算对立 | 阈值 0.7 |
| ③ 观点性复检 | 教程 / 源码解析不是反面观点 | 《零基础学 React》 |
| ④ 议题守卫 | 字面命中但说的不是这场争论 | 「过度依赖辅助驾驶」≠「反对 AI 编程助手」 |
| ⑤ 自指排除 | 把库条目自己搜回来当反方 | URL 归一化比对 |
| ⑥ 议题覆盖度 | 议题串味（顺带提一句就判过去） | 远程办公文被判成「AI 助手有益」 |

### 3.5 怎么用

```bash
# 一个库 → 一批反库条目（先 dry-run 看会怎么处理）
python first/code/run_vault.py --vault first/data/vault_demo.json --dry-run
python first/code/run_vault.py --vault first/data/vault_demo.json

# 只有链接也能跑
python first/code/run_vault.py --vault first/data/vault_url_only.json

# HTTP 接口（给前端 / 队友）
python first/code/server.py --port 8787
curl -s -X POST http://127.0.0.1:8787/antipode \
  -H 'Content-Type: application/json' \
  -d '{"url":"https://blog.csdn.net/fudaihb/article/details/136061101"}'

# 生成演示页 / 答辩看板（数字自动读实测产物）
python first/code/make_demo_page.py
python first/code/make_defense_page.py
```

### 3.6 明确不做的

- **不用 LLM 编文章**：第三档「AI 自编」仅作架构留位，默认关闭，且必须打 `synthesized: true` 并视觉区分。
- **不代用户登录**：登录态由用户自己导出 Cookie，程序只读；不存密码、不代发言。
- **不碰非观点类内容**：邮件、代码 issue、私人消息不生成反信息。
- **不训练模型**：本期全程调用现成模型 API + 确定性规则，41 条评测集是**评测集**不是训练集。

## 7. 已知局限与后续计划

| 局限 | 现状 | 下一步 |
|---|---|---|
| 检索可用率约 1/4 | 中文观点类内容分散、站点反爬 | 接入更多中文源；对站内搜索做适配 |
