# 未来电台 — 黑客松项目方案书

> 项目代号:**Echo**(回声)/ 中文名:**未来电台**
> 一句话:**录一段话,锁进时间,让它在你指定的那天回到你或他身边。**

---

## 0. 电梯陈述

**30 秒版:**
> 我们都在某些时刻说过一些话,当时很想让某个人听到,但说不出口,或者时机不对。我们做了一个产品:你录一段声音,指定一个未来的时间,它会在那天准时送到。可以送给三年后的自己,也可以送给刚出生的孩子十八岁生日那天。

**10 秒版:**
> **把你想说的话,寄给未来的某一天。**

**一句话内核:**
> 我们不做记录工具。我们做一次**时间的托付**。

---

## 1. 最重要的决定:砍掉"遗言",保留"时间"

这是这个项目能否成立的关键取舍。

### 1.1 "遗言"路线的两个死因

**死因一:承诺过重。**
用户托付的是人生最后的话。而你只是一个可能有 bug 的网站。一旦失信,后果不可挽回——所以**没有人敢用**。

**死因二:触发条件说不清。**
"如果我不在了"靠什么判断?依赖第三方死亡认证有伦理争议;不等确认又可能误发。**每一种方案都站不住。**

### 1.2 转向:纯时间 / 纯事件触发

| | 遗言电台(危险) | 未来电台(安全且一样动人) |
|---|---|---|
| 触发 | 死亡 / 重病 | **纯时间 / 纯事件** |
| 承诺 | 必须活到那一天且判断正确 | 只需活到那个日期 |
| 用户心理 | "我不敢用,万一把我坑了" | "我愿意录一段,反正到时候我也能听" |
| Demo 风险 | 评委不适 | 评委会心一笑或红眼眶 |

**做法:用户录一段话,指定一个未来的时间点送达。**

推荐场景(全是正向、温暖的):
- 给三年后考研 / 求职失败的自己
- 给刚出生的孩子,十八岁生日那天
- 给结婚五年的自己
- 给明年今天还在坚持的自己
- 给即将远行的朋友,在他落地那天

> ✅ **效果完全一样地动人,但没有任何一个伦理雷。** 这是整个项目能活下来的前提。

---

## 2. 产品结构:三层,由轻到重

### 第 1 层:录一段,封存(基础层)

- 浏览器录音 → 本地加密 → 上传
- 设定送达时间与收件人(可以是自己)
- **关键设计:封存的仪式感**

  不是"保存",是**"封存"**。按钮不是"提交",是"把它锁起来"。
  封存瞬间要有明确的视觉反馈——像把信投进邮筒、盖上火漆。

  **这一秒的仪式感,是产品的情感锚点。**

### 第 2 层:寄给某个人(社交层)

- 投递给指定的人
- 送达时同时给出"这是谁在什么时候录的"

### 第 3 层:公开胶囊墙(传播层)★

**这是让它破圈的设计,也是黑客松 Demo 的杀手锏。**

- **匿名公开信**:用户可以投一封"给全世界的信",封存到未来某天
- 到了那天,**所有当时的用户一起收到**
- 想象:2029 年的某一天,你收到一封 2026 年某个陌生人写给你的信

**为什么这一层重要:**
1. 解决"单机产品没有传播性"的问题
2. **Demo 可以现场拆一封"来自三年前的信"** —— 这是全场安静的两秒
3. 它让产品从"私人工具"变成"一个共同的时间约定"

## 3. 技术实现(真的简单)

| 模块 | 方案 | 工作量 |
|---|---|---|
| 录音 | MediaRecorder API | 半天 |
| 加密 | 前端 AES 加密后上传 | 半天 |
| 存储 | 对象存储(音频)+ 数据库(元数据) | 半天 |
| 定时送达 | 定时任务 + 邮件 / 短信通知 | 一天 |
| 封存仪式感 UI | 前端 | 一天 |

### 3.1 核心链路

```
录音 → 本地加密 → 存储 → 设定时间 → 封存(仪式)
                                    ↓
                          时间流逝(1年/3年/18年)
                                    ↓
                      到期触发 → 送达收件人 / 公开胶囊墙
```

### 3.2 数据模型

```json
{
  "capsule_id": "cap_001",
  "creator": "u_001",
  "recipient": { "type": "self | user | public", "id": "u_002" },
  "audio_url": "encrypted://...",
  "sealed_at": "2026-10-13T10:00:00Z",
  "deliver_at": "2029-10-13T00:00:00Z",
  "encryption": { "algo": "AES-GCM", "key_ref": "user_key" },
  "status": "sealed | delivered | pending",
  "message": "可选的一行附言"
}
```

### 3.3 技术选型

| 层 | 选型 |
|---|---|
| 前端 | Next.js + Tailwind |
| 后端 | Next.js Route Handlers / FastAPI |
| 存储 | 对象存储(S3 兼容)+ SQLite / Postgres |
| 加密 | Web Crypto API(前端加密,密钥不落库) |
| 定时 | 云函数定时触发 / cron |
| 通知 | 邮件(必做)→ 短信(可选) |

> **安全铁律:音频必须前端加密,密钥不由服务端持有。** 这是"托付"能成立的技术前提,也是答辩加分项。

---

## 4. 底线与伦理(必须写进产品)

因为涉及"把话留到未来",以下三条必须做:

1. **可撤回**:封存后一段时间内允许撤回(给冲动留出口)
2. **可继承**:用户长期未登录时,允许指定一位"受托人"处理胶囊(仅处理,不读取)
3. **不可窥探**:服务端**无法解密**用户音频。我们承诺"连我们都听不到"

> 第 3 条不只是技术设计,更是**产品的信任基石**。答辩时务必强调。

## 5. 48 小时开发计划

### 5.1 分工

| 角色 | 负责 | 关键交付 |
|---|---|---|
| **A — 音频与加密** | 录音 + 前端加密 + 存储 | 能录、能加密、能存、能取回播放 |
| **B — 时间与触达** | 定时任务 + 送达 + 通知 | 把 deliver_at 设成一分钟后能真的收到 |
| **C — 仪式与界面** | 封存仪式 + 播放页 + 胶囊墙 | Demo 的情感冲击全靠这里 |
| **全员** | 脚本 + 一个"假的历史胶囊" | 现场拆信那一刻 |

### 5.2 时间线

**第 1-6 小时 —— 打通链路(最关键)**
- 目标:**录一段 5 秒音频 → 加密存 → 设定 1 分钟后送达 → 真的收到**
- ⚠️ 不做美化。这条链路通了,产品就活了

**第 6-18 小时 —— 各自开发**
- A:录音交互 + 加密 + 回放
- B:定时触达 + 邮件模板
- C:封存仪式动画 + 播放页

**第 18-30 小时 —— 胶囊墙 + 集成**
- 做出公开胶囊墙
- **准备一封"来自三年前的信"作为演示素材**(这一条极其重要)

**第 30-40 小时 —— Demo 打磨**
- 仪式感动画、声音、节奏
- **录制备用视频**

**第 40-48 小时 —— 答辩准备**
- 讲清"砍掉遗言、保留时间"的取舍智慧(这是最加分的地方)

### 5.3 风险预案

| 风险 | 预案 |
|---|---|
| 浏览器录音权限失败 | 备用:支持上传音频文件 |
| 邮件送达被拦截 | 演示时用站内通知 + 截图兜底 |
| 现场不敢录真话 | **预先录好**一段,现场只演示流程 |
| 情绪失控讲不下去 | 提前排练,控制节奏 |
| 被质疑伦理 | 用第 4 节的"三可"原则正面回应 |

## 6. Demo 脚本(3 分钟版)

### 开场(25 秒)—— 用一个具体的人开场

> "我有一个朋友,他父亲去年走了。走之前,他父亲的手机里留了一段语音,是两年前随手录的一段叮嘱。**他到现在都不敢删。**
>
> 我们想做的产品,就是让这样的声音,不用靠运气才能留下来。"

### 演示一(50 秒)—— 现场封存

（现场录一段 15 秒的话,或播放预录内容）
> "我现在录一段话给三年后的自己。"

展示:录音 → 点击"封存" → **仪式动画**(火漆封缄 / 信箱落锁)→ 显示"将于 2029-10-13 送达"

### 演示二(30 秒)—— 证明它真的会到

（演示设定的"一分钟后送达"演示胶囊）

收到 → 点开播放 → 声音响起来。

> "这不是一个存了就不管的产品。**它是真的会送达的。**"

### 高光(45 秒)—— 公开胶囊墙 ★

打开胶囊墙,找到一封**"来自三年前的匿名信"**,现场点开。

> "这是一封三年前,某个陌生人写给今天所有人的信。"

（播放。全场安静。)

> "**我们想做的,不是一个录音工具。是想让一些话,有机会穿越时间。**"

### 收尾(25 秒)—— 回到技术承诺

> "最后说一件我们很在意的事:**这些音频是加密的,密钥不在我们手里。**
>
> 也就是说,**连我们,都听不到你在信里说了什么。**"

## 7. 评审问答预案

**Q:这和普通的"埋时间胶囊"应用有什么区别?**
A:三点。一是**公开胶囊墙**——三年后的某天,一群人一起收到一批陌生人的信,这是共同的时间约定;二是**端到端加密**,服务端无法解密;三是**轻触达**,用户设定后完全无需操作,到期自动送达。

**Q:为什么不直接做遗言?**(很可能会被问)
A:（**这是最关键的答辩点**）我们认真考虑过,然后主动放弃了。因为"遗言"有两个无解的问题:**一是承诺过重**——用户托付的是人生最后的话,产品一旦失信,无法挽回;**二是触发条件说不清**——"如果我不在了"靠什么判断?存在伦理争议。所以我们转向**纯时间触发**——**效果一样动人,但把风险降到了零。** 这是我们做的最重要的一个产品决定。

**Q:数据安全怎么保证?**
A:音频在**用户浏览器内加密**,密钥不由服务端持有。服务端存储的是密文,**连我们自己也听不到内容**。

**Q:为什么用户会信你不会哪天关站?**
A:（**诚实回答**)这是这类产品的根本问题。我们的答案是三个设计:**可撤回**(封存后短期可撤)、**可继承**(指定受托人)、**加密不可窥探**(即使服务停止,密文也无法被滥用)。我们建议这个产品的长期形态是开源 + 可自托管。

**Q:商业模式?**
A:免费基础版(个人胶囊)+ 付费(公开胶囊墙、长周期存储、实物寄送 DVD / U 盘作为纪念)。

**Q:技术难点?**
A:不在录音和存储,在**定时送达的可靠性**——几年后仍然准确触达,需要长期可信的调度与通知链路。这是产品的生命线。

## 9. 为什么这个项目值得做(给自己的备忘)

它和其他项目有一个根本区别:**别的产品优化效率,它优化"遗憾"。**

技术上,它简单到三天能做完。但它的价值不在技术,在**你敢不敢认真对待一件柔软的事**。

**黑客松上,大部分团队在比谁的技术更硬。而这个项目,比的是谁更敢温柔。**

**一句话总结:我们不做记录工具。我们做一次时间的托付。**
