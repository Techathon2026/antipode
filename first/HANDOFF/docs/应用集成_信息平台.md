# 接进桌面应用：左侧加一栏「我的信息平台」

> 目标形态（你说的）：
> 左侧新增「我的信息平台」→ 用户自己添加平台（知乎 / GitHub）→ 每个平台一个库
> → 点进去看他筛过的信息 → 合适的信息带反推荐 → **反推荐可以按平台开关**。
>
> 这篇是**接线说明**，不是构想。后端已经写好并跑通：`code/app_api.py`。

---

## 1. 一句话架构

```
桌面应用（Electron/其它）
   ├─ 左侧菜单新增「我的信息平台」
   ├─ 页面调本地后端 http://127.0.0.1:8790
   └─ 后端 code/app_api.py
         ├─ 采集：collect_github.py / collect_zhihu.py / collect_account.py / build_vault.py
         ├─ 建库：build_vault.py（判立场、写省流）
         └─ 反推荐：run_vault.py（按库开关决定跑不跑）
```

**为什么是本地 HTTP，不是把 Python 塞进 Electron 主进程**
- 三条采集链路都要起浏览器、要长任务、要断点续跑，天生适合独立进程；
- 崩了不拖垮界面，重启后端即可恢复（状态落在 `data/platforms.json`）；
- 将来要换成队友的库/模型，只改后端，界面不动。

**为什么不用 `code/server.py`**
`server.py` 是给队友的单条能力接口（一条 URL → 反库条目），**只读、无状态**。
桌面应用要的是状态：加了哪些平台、每个平台一个库、这条有没有反推荐。
两件事混在一个服务里会互相牵制，所以分成两个进程，各自职责清楚。

## 2. 接口契约（前端照着做就行）

启动：`python code/app_api.py --port 8790`（默认只听 127.0.0.1）

### 2.1 平台列表（左侧菜单点进去的首屏）

```
GET /platforms
→ {"ok":true,"count":1,"platforms":[{
     "id":"zhihu-a1b2c3","platform":"zhihu","label":"知乎",
     "input":"微服务","antipode_enabled":true,
     "item_count":10,"eligible_count":9,"antipode_count":16,
     "status":"done","last_stage":"完成：10 条信息，9 条可反推荐，16 条反信息",
     "antipode_supported":true,
     "created_at":"...","last_run":"..."}]}
```

卡片上建议显示：`label` + `item_count` + `eligible_count` + 反推荐开关状态。

### 2.2 添加平台

```
POST /platforms
{"platform":"zhihu", "label":"知乎 · 我关注的", "input":"微服务",
 "limit":10, "antipode_enabled":true}
→ 201 {"ok":true,"platform":{...},"job":{"id":"j-xxx","status":"running"}}
```

`platform` 取值与各自要填的 `input`：

| platform | input 是什么 | 认证 | 能做反推荐 |
|---|---|---|---|
| `github` | 留空 = 最近 N 天最热的新项目；填 `python` 这类 = 只看该语言 | 可选只读 token（不填用本机凭据） | ❌ 仓库没有立场 |
| `zhihu` | 议题关键词（如「微服务」）；留空 = 热榜 | 第一次要弹窗登录 | ✅ 观点长文 |
| `douyin` / `weibo` | 主页链接（留空 = 打开平台首页自己进） | 第一次要弹窗登录 | ❌ 正文太短 |
| `url` | 一串文章链接，一行一个 | 不需要 | ✅ 观点文章 |

**反推荐默认关**（`antipode_enabled: false`）。平台支持是一回事，用户要不要是另一回事。

### 2.3 采集进度（前端轮询，2~3 秒一次）

```
GET /jobs/{job_id}
→ {"ok":true,"job":{"status":"running|done|failed","stage":"正在为 9 条适合的内容找反面",
                    "progress":["  滚了 3 次，页面高度 11961px…", ...],
                    "result":{"items":10,"eligible":9,"antipode":16},"error":""}}
```

`stage` 直接显示在界面上就行——它本来就是给人读的中文（"找到 2 个，开始读 README"）。
`progress` 是最近 200 行原始输出，可以收进"查看详情"里。

> 实测耗时：GitHub 2 条约 15 秒；知乎 10 条（含量立场 + 反推荐 9 条）约 15 分钟。
> **前端必须做进度条**，否则用户会以为卡死。

### 2.4 库里的信息（点进某个平台后看的）

```
GET /platforms/{id}/items?only=all|eligible&q=关键词
→ {"ok":true,"count":9,"items":[{
     "id":"u-e41d0fcc90","title":"微服务入门这一篇就够了",
     "url":"https://zhuanlan.zhihu.com/p/381847108",
     "summary":"微服务架构通过服务注册中心和配置管理解决单体…",
     "kind":"opinion","text_chars":10259,
     "antipode_eligible":true,"antipode_reason":"",
     "antipode":[{"title":"从微服务走向单体化",
                  "url":"https://www.v2ex.com/t/1106152",
                  "takes_side":"单体","opposition_score":0.95,
                  "summary":"CEO 因微服务部署复杂…",
                  "evidence_span":"CEO 觉得微服务部署极其繁琐…",
                  "synthesized":false}]}]}
```

界面分支很简单：

- `antipode_eligible=false` → 只显示摘要 + 原文链接，**不给"看反面"按钮**
  （`antipode_reason` 有原因，可挂在 tooltip 上）
- `antipode_eligible=true` 且 `antipode` 非空 → 显示反推荐卡片
- `antipode_eligible=true` 但 `antipode` 为空 → 显示"这条暂时没找到合格的对面"（不是故障）
- `synthesized=true` → **必须做视觉区分**（我们的硬规矩：AI 自编默认关闭，前端要标出来）

### 2.5 反推荐开关（按平台）

```
PATCH /platforms/{id}
{"antipode_enabled": false}
→ {"ok":true,"platform":{...},"changed":["antipode_enabled"]}
```

两件事要说清楚：

1. **关掉之后再采集，`run_vault` 会直接拒绝生成**（它读库里这个字段），
   而不是"生成了但不显示"。用户的选择应该体现在产物上。
2. 对不支持的平台（GitHub/抖音/微博）打开会返回 400 + 原因，前端直接展示这句：
   `GitHub 只做信息收集：仓库没有「对立面」`。

### 2.6 其它

```
GET    /health                  能力清单（平台、认证方式、是否支持反推荐）
GET    /platforms/{id}          单个平台详情
POST   /platforms/{id}/refresh  重新采一次（异步，返回 job）
DELETE /platforms/{id}          移除平台（连带删掉这个库的三个文件）
```

## 3. 界面上最关键的三个决定（不是随便定的）

**① 一个平台 = 一个库，不是一个平台 = 一堆条目。**
你要的是"点进去看这个平台筛出来的东西"，那么"库"就是用户能理解的单位。
底层确实做到了：每个平台的库 id 就是 `platform.id`，文件是 `vault_<id>.json`。

**② `antipode_eligible` 是条目级、`antipode_enabled` 是库级。**
用户可能想要"知乎开、GitHub 关"。而具体某一条能不能找反面，是内容决定的
（一条视频、一个代码仓库、一篇教程，没有"对立面"）。两级分开，界面才不会说谎。

**③ 不可反推荐的条目也要显示，并给原因。**
它们不是失败品——「今天这 10 条里，只有 1 条值得找反面」本身就是信息。
把丢弃原因做成可见的（`antipode_reason`、`data/*.junk.jsonl`），
比"静悄悄过滤掉"更可信，答辩时也是加分项。

## 7. 一个必须提前说清的边界

**「用户加平台」不等于「我们帮他登录」。**

- GitHub：只读 token（用户自己生成，我们只读）
- 知乎 / 抖音 / 微博：**弹窗让用户自己登录**，程序只复用本机登录态目录

不做"拿账号密码 POST 登录表单"，原因写在 `docs/账号采集_说明.md` 第 2 节：
三家登录都有验证码/设备校验，脚本一登即红；密码落盘是这类应用最贵的一类漏洞。

界面上对应的话术建议：**「替你省了打字，没有替你保管密码。」**
