## 0. 一句话说清要做什么

**输入:** 一段文本
**输出:** 这段文本对某个议题**站在哪一边**,以及**凭什么这么判断的原文证据**。

```json
{
  "issue_id": "microservices_vs_monolith",
  "supports": "单体",
  "strength": "strong",
  "confidence": 0.88,
  "evidence_span": "一个下单请求要跨七个服务,排障时间翻了三倍",
  "reasoning": "未直接表态,但罗列的全是负面后果"
}
```

模型输出的是 **`supports`(文本支持的那一方)**,
代码再把它归一成机器用的 `side` 键:**`"a"` / `"b"` / `"neutral"` / `"undetermined"`**。

## 1. ★ 三个必须一开始就做对的设计

### 设计一:直接标"支持哪一方",不要标 pro/con

**这是全系统最重要的一条约定。**

每个议题预先定义两个对立面:

```python
{"issue_id": "react_vs_vue", "side_a": "React", "side_b": "Vue"}
```

模型只需要回答:**文本支持 React,还是 Vue?**

| 写法 | "推荐 Vue" 该怎么标 | 问题 |
|---|---|---|
| ❌ `polarity: pro/con` + `target` | `target=React, polarity=con`?还是 `target=Vue, polarity=pro`? | **同一句话两种合法标法**,反仓库无法对齐 |
| ✅ `supports: "Vue"` | `supports="Vue"` | 唯一确定 |

**取反仓库的对立面只需一行:**

```python
opposite = issue["side_b"] if stance.side == "a" else issue["side_a"]
```

`neutral` / `undetermined` 没有对立面 —— 这也是为什么它们必须被排除出反仓库。

### 设计二:议题必须从预定义清单里选,不许自创

如果让 LLM 自创议题,它会发明出你语料库里根本没有对立面的议题——**你就永远找不到反信息。**

清单在 `code/stance_extractor.py` 的 `ISSUE_TAXONOMY`,当前 16 个:

| issue_id | 议题 | side_a | side_b |
|---|---|---|---|
| microservices_vs_monolith | 微服务 vs 单体架构 | 微服务 | 单体 |
| tdd_necessity | 测试驱动开发是否必要 | 先写测试 | 先写实现 |
| monorepo_vs_multirepo | 单仓 vs 多仓 | 单体仓库 | 多仓库 |
| react_vs_vue | React vs Vue | React | Vue |
| rest_vs_graphql | REST vs GraphQL | REST | GraphQL |
| orm_or_raw_sql | ORM 还是手写 SQL | ORM | 手写 SQL |
| typescript_strictness | TypeScript 严格模式是否值得 | 开严格模式 | 关严格模式 |
| oop_vs_fp | 面向对象 vs 函数式 | 面向对象 | 函数式 |
| ai_assistant_weakens_dev | AI 编程助手是否让程序员退化 | AI 助手有害 | AI 助手有益 |
| remote_vs_onsite | 远程办公 vs 坐班 | 远程办公 | 坐班 |
| rust_vs_cpp | Rust 还是 C++ | Rust | C++ |
| cloud_vs_selfhost | 上云 vs 自建 | 上云 | 自建 |
| code_review_strictness | 严格 Code Review 是否值得 | 严格评审 | 宽松评审 |
| static_vs_dynamic_typing | 静态类型 vs 动态类型 | 静态类型 | 动态类型 |
| tabs_vs_spaces | 缩进用 Tab 还是空格 | Tab | 空格 |
| tofu_pudding | 甜豆腐脑 vs 咸豆腐脑 | 甜豆腐脑 | 咸豆腐脑 |

> 💡 清单顺序无所谓,但 **`issue_id` 一旦定下就不能改** —— 它是全系统的外键。
> ⚠️ 严禁加入政治、宗教、地域类议题,现场审核零风险。

### 设计三:分两步 —— 先议题对齐,再判立场

| | 一步做完(❌) | 分两步(✅) |
|---|---|---|
| 议题一致性 | 差(会出现"微服务"/"微服务架构"/"Microservices"三种写法) | 好(强制走清单) |
| 能否按议题聚合 | ❌ | ✅ |
| 能否找到反信息 | ❌ 找不到对应的反面 | ✅ 有确定的对立面 |

在代码里这体现为:**清单随 prompt 一起传进去,模型只能从里面挑 `issue_id`。**
代码再做一次硬校验,不在清单里的一律丢弃并计入 `invented_issue` 指标。

## 2. 核心 Prompt

见 `code/stance_extractor.py` 的 `SYSTEM_PROMPT`。要点:

```
1. issue_id 必须来自给定清单, 不许自创。
2. supports 必须原样填该议题的 side_a 或 side_b 文本, 或 "neutral" / "undetermined"。
3. 立场是文本【实际表达】的立场, 不是作者的自我声明。
4. evidence_span 必须是原文的【精确子串】, 一个字都不能改。
5. 讽刺、反话按【实际含义】判断。
6. 只引用/转述他人观点的 → "undetermined"。
7. 中立讨论两面 → "neutral"。
8. 注意【隐含立场】。
9. 只提到词、没表达立场的 → 不要输出。

【判断 supports 的方向】
- 夸 A 骂 B           → supports = A
- "我选了 A"、"我们用 A" → supports = A
- 罗列的全是 A 的坏处    → supports = A 的对立面
- 两边各打五十大板      → "neutral"
```

**few-shot 覆盖 7 种情况**(直接支持 / 隐含反对 / 讽刺 / 转述 / 中立 / 多议题 / 无立场)。
其中**隐含反对**和**只提到名词不输出**这两条最关键:

- `"我们去年上了微服务,结果排障时间翻了三倍。"` —— **一个字没提"反对"**,但立场清楚
- `"本周分享会主题包括微服务、GraphQL 和 Kubernetes。"` —— **必须输出空数组**,否则反仓库会被名词灌满

## 3. ★ 证据校验闸门(最便宜的防幻觉手段)

让模型输出证据原文,然后用**代码**验证它真的存在于原文里。

```python
def verify_evidence(text: str, span: str) -> bool:
    if not span or len(span.strip()) < 4:
        return False
    return normalize(span) in normalize(text)   # 归一化后再做子串匹配
```

| 情况 | 说明 |
|---|---|
| 证据存在 | 模型确实基于原文判断,可信 |
| 证据不存在 | **模型在编** → 直接丢弃 |

**归一化是必须的**:`normalize()` 会去掉所有空白与中英标点。
否则 `"排障时间翻了三倍。"`(带句号)会被误判为"原文里没有",白白丢掉正确结果。

**重试策略(v2 修正了一个烧钱 bug):**

```python
for _ in range(MAX_RETRY + 1):        # MAX_RETRY = 1
    raw = call_llm(text, taxonomy)
    if not raw["stances"]:
        break                          # 模型明确判断"无立场" → 合法结论, 不重试!
    ...校验...
    if results:
        break
    # 有原始输出但全部被丢弃 → 疑似幻觉, 值得重试一次
```

> ⚠️ 旧版无论什么情况都重试 2 次。但"这段文本没有立场"是**正常且常见的结论**,
> 对它重试只会把成本翻三倍,结果还是一样。**只在疑似幻觉时才重试。**

## 4. 置信度阈值策略

```python
def gate(side: str, confidence: float) -> str:
    if side in ("neutral", "undetermined", "unknown"):
        return "reject"          # 未站队 → 绝不进反仓库
    if confidence < 0.6:
        return "reject"
    if confidence < 0.8:
        return "review"          # 可用于仓库, 不进反仓库
    return "accept"              # 全流程可用
```

**关键原则:反仓库的门槛要比仓库高一档。**

理由:仓库错了只是"推了条不相关的信息";反仓库错了是"给用户塞了条莫名其妙的反对意见",**伤害大得多**。

## 5. 难例与对策(速查表)

| 难例 | 例子 | 对策 |
|---|---|---|
| **隐含立场** | "上完微服务,排障时间翻三倍" | Prompt 规则 8 + few-shot 示例 2 |
| **讽刺反话** | "微服务真是太棒了——搭了两周健康检查" | Prompt 规则 5 + few-shot 示例 3 |
| **仅转述** | "A 认为…而 B 认为…" | 标 `undetermined`,强制排除 |
| **neutral vs undetermined** | 见下方专节 | **不要改 prompt**,见结论 |
| **多重立场** | 一篇文章分别评价三种架构 | 输出数组,每议题一条 |
| **对比式** | "相比 React,Vue 更好" | 输出 `supports="Vue"` **一条**即可,不必输出两条 |
| **只是提到名词** | "分享会主题包括微服务" | 不输出(规则 9) |

### ★ neutral vs undetermined:一条实测过、但**决定不再优化**的边界

这是实测中**唯一稳定出错的类别**。理论上判据很清楚:

> **看"作者本人有没有出面下判断",而不是看"有没有出现正反两面"。**

| | 特征 | 例 |
|---|---|---|
| `undetermined` | 通篇只是转述/引用,**作者本人从头到尾没出面** | "Fowler 认为它适合复杂系统,而 Brown 认为大多数团队不需要它。" |
| `neutral` | **作者本人出面**了,而且表的是"不站队" | "都挺好用的,选哪个看团队习惯。" |

**但这是实战结论:`不要为它改 prompt`。** 我们用同一套评测集做了三次受控实验:

| 版本 | 4 分类 | 有效立场 | 排除判定 | 议题对齐 | 失败数 |
|---|---|---|---|---|---|
| **原始 prompt** | **90.2%** | **94~100%** | **100%** | **97.6~100%** | 4 |
| 改判据 + 2 个对照 few-shot | 87.8% | 91.4% | 100% | 97.6% | 5 |
| 改判据、不加 few-shot | 85.4% | 91.4% | 100% | 95.1% | 6 |

**判据写得越"清楚",整体反而越差**——因为长出来的规则文字把模型的注意力从"判立场"上牵走了,
连带把原本判对的讽刺反话、豆腐脑方向、议题对齐都弄错了。**已全部回滚。**

**为什么可以安心不修:** `gate()` 里 `neutral` 和 `undetermined` **都返回 reject**,
产品行为完全相同(都不进仓库、不进反仓库)。混淆这两个标签对产品**零影响**。
区分它只是为了报告好看,而修它的代价是真实的 a/b 准确率下降 —— **这笔账不划算。**

> ⚠️ **一条额外警告(踩过的坑)**:我第一版改动里把评测集的原句直接写进了 prompt 规则里
> (例如把"这事儿一直没有定论"当例子)。**这是"对着答案考试",指标会虚高且不可信。**
> 改 prompt 时,示例句子必须是**现写的**,不能从 gold set 里搬。

> ⚠️ **另一条更隐蔽的坑**:不要只跑一轮就下结论。见下面第 8 节"评测有噪声"。

## 6. 长文本怎么处理

```python
def extract_long(text, taxonomy, chunk_size=3000, overlap=200):
    chunks = split_with_overlap(text, chunk_size, overlap)
    all_stances = []
    for c in chunks:
        all_stances += extract(c, taxonomy)
    return merge_stances(all_stances)   # 同议题多条 → 取置信度最高
```

**注意 overlap(重叠)**,否则立场可能正好被切在分片边界上,两边都抽不出来。

## 8. 怎么验证它准不准(别跳过)

评测集在 `code/gold_set.jsonl`,当前 **41 条**,覆盖全部 16 个议题。

**格式:**

```jsonl
{"text": "我们去年上了微服务, 排障时间翻了三倍。", "issue": "microservices_vs_monolith", "side": "b"}
{"text": "关于微服务, Fowler 认为…而 Brown 认为…", "issue": "microservices_vs_monolith", "side": "undetermined"}
{"text": "豆腐脑当然要吃甜的。", "issue": "tofu_pudding", "side": "a"}
```

`side` 取值:`"a"` / `"b"` / `"neutral"` / `"undetermined"` —— **和清单里的 side_a / side_b 对应**。

**要测五个指标**(前三个是 v4 起拆出来的,拆的理由见下):

| 指标 | 说明 | 目标 |
|---|---|---|
| **立场准确率(4 分类)** | `side` 严格判对的比例 | > 80% |
| ├ **有效立场准确率** | 只看期望 `a`/`b` 的样本 —— **决定仓库/反仓库放得对不对** | > 85% |
| └ **排除判定准确率** | 只看期望 `neutral`/`undetermined` 的样本 —— **决定该丢的有没有丢掉** | > 85% |
| **议题对齐准确率** | `issue_id` 选对的比例 | > 90% |
| **证据校验通过率** | 证据真的在原文里的比例 | **> 95%** |
| **自创议题率** | 模型发明清单外议题的比例 | 0% |

> **为什么要拆成三个而不是只看一个?**
> `neutral` 和 `undetermined` 在下游 `gate()` 里都返回 `reject`,**产品行为完全相同**。
> 所以模型在这两个标签之间摇摆,对产品是零影响,却会把严格 4 分类的分数拉低。
> 拆开报,才能分清两种情况:
> - **有效立场准确率掉了** → 真出事了,仓库/反仓库会放错东西,必须修
> - **只有 4 分类掉了、有效 + 排除都没掉** → 只是两个等价标签之间摇摆,不影响交付
>
> 答辩时这句话很有用:"我们的错误只集中在无产品影响的分支上。"

> **证据校验通过率最重要。** 低于 95% 说明模型在编证据,必须回去改 prompt。
>
> ⚠️ v1 的这个指标**恒等于 100%**,因为失败样本已经被丢弃、分母里根本不含它们。
> v3 把分母改成"模型产出的原始条数",这个指标才真正有意义。

### 两套评测集

| 文件 | 条数 | 用途 |

### ★★ 评测有噪声:同一个 prompt 重跑,失败条目会变

**这是本项目最重要的一条工程经验,踩过一次才发现的。**

实测:**字节级完全相同的 prompt**,连跑两次,结果不同:

| | 4 分类 | 有效立场 | 议题对齐 | 失败条目 |
|---|---|---|---|---|
| 第 1 次 | 90.2% | 100% | 100% | L10, L15, L21, L27 |
| 第 2 次 | 90.2% | 94.3% | 97.6% | **L3**, L21, L27, **L37** |

`L21`/`L27` 两次都错(真实弱点);但 `L10`/`L15` 和 `L3`/`L37` 在两次之间**互相翻转**——
**这就是纯粹的采样噪声。** 4 分类数字碰巧一样,纯粹是巧合。

**后果:单轮评测的分数不能用来指导 prompt 调优。** 否则你会在噪声上来回调 prompt,永远收敛不了。

#### 还有个更阴险的陷阱:服务端缓存会伪装成"完全确定性"

改 prompt 的过程中,我曾连续跑三次**完全一致**(连失败条目都一样),一度以为模型是确定性的。
但把 prompt 逐字节核对回原版后重跑,结果又变了 —— 说明前三次的一致**是服务端缓存造成的假象**,
不是模型真的确定。

> **所以:不要"连续紧挨着"重跑同一个 prompt 来测稳定性**,那样很可能全部命中缓存,
> 得到 100% 一致并得出错误结论。

#### 正确的做法

1. **改 prompt 前先跑 3 轮基线**,记下每轮数字 → 得到**波动区间**(本项目约 ±1~2 条 / ±3~5%)
2. 改动后跑 3 轮,只有当**改善幅度明显超出波动区间**时才认
3. **不连续重跑**,每轮之间隔开几分钟,避免命中缓存
4. 更盯**失败集合的稳定性**,而不是单看一个总分:
   - 每轮都错 → 真实弱点,值得修
   - 时对时错 → 噪声,别追

**推荐命令(轮次之间要间隔):**

```powershell
# 第 1 轮
python stance_extractor.py --eval gold_set.jsonl
# 等几分钟再做第 2 轮,避免服务端缓存
python stance_extractor.py --eval gold_set.jsonl
```

> 答辩时可以主动说这一点:"我们测出了评测的噪声区间,所以只接受超出噪声的改进。"
> **这比报一个孤立的高分更能体现你们的工程严谨性。**

## 10. 三个最容易踩的坑

### 坑一:让模型自创议题
→ 结果:找到的议题没有对立面,反仓库建不起来。
**对策:强制走清单 + 代码硬校验。**

### 坑二:把"引用"当成"立场"
→ 结果:给用户生成一堆错的反信息。
**对策:`undetermined` 必须排除出反仓库流程。**

### 坑三:不做证据校验
→ 结果:模型编了证据你也不知道,上线才发现质量崩了。
**对策:代码验证子串。零成本保险,答辩时也硬气。**
