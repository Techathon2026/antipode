# 反推荐引擎 — 黑客松项目方案书

> 项目代号:**Counterpoint**(反调)
> 一句话:**一个刻意跟你作对的推荐引擎——它不喂你想看的,它给你看"最聪明的人是怎么反对你的"。**

---

## 0. 电梯陈述

**30 秒版:**
> 所有推荐算法都在做同一件事:让你更确信自己是对的。我们的产品反过来——它先搞清楚你相信什么,然后去**找出这个观点最有力的反驳**,连论证带出处一起给你。它不是让你改变立场,是让你**知道自己的立场站在什么地方**。

**10 秒版(评委路过):**
> **信息茧房的解药,不是给你更多信息,是给你一个真正的对手。**

**一句话内核:**
> 别人让你更舒服,我们让你更扎实。

---

## 1. 关键决定:话题必须锁定「安全对立区」

这是整个项目最重要的一步取舍。若不锁定,项目会死于三个风险:**内容源不稳定、立场标注无标准、话题审核风险**。

### 1.1 只在"有真实对立、且绝对安全"的领域工作

**推荐的话题域(MVP 只用这一域):**

| 领域 | 对立示例 | 为什么安全 |
|---|---|---|
| 编程语言 / 框架之争 | Tabs vs Spaces、React vs Vue、OOP vs FP | 有真实论点、素材海量、零政治风险 |
| 工程方法论 | 微服务 vs 单体、敏捷 vs 瀑布、测试先写 vs 后写 | 有文档、有论证、有历史争议 |
| 产品与设计理念 | 直觉设计 vs 数据驱动、极简 vs 功能全 | 争议丰富,有公开案例 |
| 学术方法论 | 实验优先 vs 理论优先、频率派 vs 贝叶斯 | 论证严谨,适合展示"论证链" |
| 生活偏好 | 甜豆腐脑 vs 咸豆腐脑、猫派 vs 狗派 | 轻松幽默,适合 Demo 开场破冰 |

**明确排除(写进方案,体现边界感):**
政治、宗教、民族、地域攻击、任何可能涉及人身/群体的敏感议题。

> 💡 **把"甜咸豆腐脑"放在 Demo 的第一个例子。** 它让评审先笑,证明产品不是挑衅工具;然后再展示"微服务 vs 单体"这种有分量的例子,证明它有真本事。**一轻一重,节奏就出来了。**

### 1.2 收获:项目立刻变得可实现

限定话题域之后:
- **内容源有解** —— 技术争议内容在海量公开博客/技术社区/论文里,且可合法获取
- **立场有解** —— 技术立场的标注标准是相对客观的(有论证、有前提、有结论)
- **审核无险** —— 完全避开高风险议题

## 2. 产品三层设计(从浅到深,这是产品的筋骨)

### 第 1 层:反推荐(基础层)

用户表达兴趣 → 系统推送**立场对立**的内容。

- 输入:"我在用 React"
- 输出:"这是 Vue 社区最有力的三个反驳,以及一个认为两者都错了的观点"

**⚠️ 只做到这一层 = 一次性笑话。必须有下面两层。**

### 第 2 层:观点体检(增值层)

看完一批内容后,**给用户的认知画一张地图**。

- "你在 8 个议题上有明确立场"
- "其中 3 个议题,你的立场存在内部矛盾"
- 例:你主张"代码要简洁",同时主张"必须写详尽注释和防御性检查"——这两者需要你解释清楚

**这一层让产品从"帮你换角度"升级为"帮你看清自己"。**

### 第 3 层:最强反对者机制(灵魂层)★

**这是产品的核心竞争力,也是 Demo 的高光。**

不要推随机对立言论(会变成杠精垃圾场)。要做:

> **针对用户支持的每一个观点,自动检索并生成"这个观点最有力的反驳"。**

约束条件(缺一不可):
1. **必须带论证链** —— 不是"我反对",而是"因为 X,所以 Y,因此 Z"
2. **必须有出处** —— 引用原文,可点击验证(与技术项目"回现场"同源能力)
3. **必须是"最强的那个"** —— 系统需要在候选反驳中做质量排序

**"陪你看世界另一边"是情怀,"帮你找到最强的那个反对意见"是能力。**

## 3. 系统架构

```
① 输入层   用户立场表达(文字)
                 ↓
② 解析层   立场抽取 → 结构化立场图(议题 / 方向 / 前提)
                 ↓
③ 检索层   对立内容检索 + 论证链提取 + 质量排序
                 ↓
④ 呈现层   反调解读卡(论点/论证/出处) + 观点体检报告
```

### 3.1 核心数据结构:立场图(Stance Graph)

```json
{
  "user_id": "u_001",
  "stances": [
    {
      "topic": "前端框架",
      "stance": "prefer_react",
      "direction": "pro",
      "premises": ["组件生态成熟", "招聘市场大"]
    },
    {
      "topic": "代码风格",
      "stance": "prefer_concise",
      "direction": "pro",
      "premises": ["可读性优先"]
    }
  ],
  "conflicts": [
    {
      "pair": ["prefer_concise", "require_defensive_checks"],
      "reason": "简洁与防御性检查在同一段代码中可能冲突"
    }
  ]
}
```

### 3.2 反驳数据结构:论证卡(Argument Card)

```json
{
  "target_stance": "prefer_react",
  "counter_claim": "在中小型项目中,框架选择的影响被高估",
  "argument_chain": [
    "前提 1: 项目规模决定架构收益",
    "前提 2: 大多数项目生命周期 < 3 年",
    "结论: 生态成熟度的收益难以兑现"
  ],
  "source": {
    "title": "原文标题",
    "url": "https://...",
    "author": "...",
    "quote": "支持该论证的原文片段"
  },
  "strength_score": 0.87
}
```

> **`source.url` + `quote` 是信任的关键。** 每条反驳都能一键跳回原文——这是"可审计"的物理基础。

### 3.3 可审计规则(应对"你自己有没有立场"的必问)

- 每次判定"这是对立观点"时,**展示打了什么标签、依据是什么**
- 用户可对判定**提出异议**,系统必须回应
- 规则公开,可被检视

**当你能把"我为什么这么推"摊开给用户看时,项目就从"有趣的想法"变成了"有方法论的系统"。**

## 4. 技术选型

| 层 | 选型 | 理由 |
|---|---|---|
| 前端 | Next.js + Tailwind | 卡片式 UI 出活快 |
| 立场抽取 | LLM(结构化输出 / function calling) | 直接产出 JSON 立场图 |
| 内容检索 | 预建语料池 + 向量检索 | 见第 5 节,MVP 用预建语料 |
| 论证抽取 | LLM + 规则校验 | 需强制输出"前提/结论"结构 |
| 质量排序 | 打分模型(LLM 打分 + 规则过滤) | 过滤杠精内容 |
| 摘要 | OpenAI API | 手头已有 |

> **核心原则:** 检索用代码,判断和生成用模型。不要把整个产品做成一个大 prompt。

## 5. 最棘手的问题:内容源怎么来(必须提前解决)

**这是这个项目唯一可能卡死你的地方。** 三个方案,按推荐度排序:

### 方案 A(★ 强烈推荐):预建小型精选语料池
- 手工整理 **50-100 组**高质量"观点 vs 反驳"配对
- 来源:知名技术博客、论文、技术社区高赞回答
- 优点:**可控、可审、质量高、零法律风险**,48 小时完全够用
- 缺点:覆盖面有限 —— 但黑客松 Demo **根本不需要全覆盖**

> **Demo 只需要在 5-10 个预设话题上做到丝滑,就足够赢。** 别追求通用。

### 方案 B:公开 API 检索
- 用公开搜索 API + LLM 筛选
- 风险:质量不稳定、可能有法律/条款问题
- 仅作为"锦上添花",不作为主线

### 方案 C:实时爬取
- **不推荐。** 法律风险、稳定性差、Demo 现场容易翻车

## 6. 48 小时开发计划

### 6.1 分工(有队友)

| 角色 | 负责 | 关键交付 |
|---|---|---|
| **A — 语料与数据** | 整理 50-100 组观点/反驳配对 + 标注 | 一个能查的高质量语料池 |
| **B — 立场与论证** | 立场抽取 + 论证链生成 + 质量排序 | 输入立场 → 输出论证卡 |
| **C — 前端与呈现** | 反调卡片流 + 观点体检报告 + 出处跳转 | Demo 界面有冲击力 |
| **全员** | 话题安全边界 + Demo 脚本 | 3 分钟讲清且有笑点 |

### 6.2 时间线

**第 1-6 小时 —— 打通一条链路(最关键)**
- 目标:**硬编码一个用户立场**("我用 React")→ 输出**一张**带论证链和出处的反驳卡
- ⚠️ 这一步不做美化,不做多个话题

**第 6-18 小时 —— 各自开发**
- A:语料池扩充到 50 组,标注质量
- B:立场抽取 + 论证结构生成 + 打分排序
- C:UI 骨架 + 卡片"出处跳转"

**第 18-30 小时 —— 集成 + 观点体检**
- 打通完整闭环;**做出"观点体检"那张图**(这是记忆点)

**第 30-40 小时 —— Demo 打磨**
- 选 3 个话题做精:一个好笑(豆腐脑)、一个有料(微服务 vs 单体)、一个有争议(测试先写 vs 后写)
- **录制备用视频**

**第 40-48 小时 —— 答辩准备**
- 讲清"可审计"和"最强反对者"两个方法论
- 准备问答预案

### 6.3 风险预案

| 风险 | 预案 |
|---|---|
| 论证质量不稳定 | 预跑 3 个话题,固定话术;语料提前人工校验 |
| 被质疑有立场 | 用"可审计规则"正面回应(见 3.3) |
| 现场被问敏感话题 | 明确说明产品限定在"技术/生活偏好"域 |
| 内容不够 | 语料池提前备足,别现场检索 |
| 时间不够 | **保"一张反驳卡 + 出处跳转 + 观点体检"三件事** |

## 7. Demo 脚本(3 分钟版)

### 开场(25 秒)—— 用提问制造张力

> "我想先说一个不太舒服的事实:**推荐算法比你自己更懂你想看什么,但它从来不想让你不舒服。**
>
> 结果就是,我们越来越确信自己是对的——因为从来没有人认真地反对过我们。
>
> 我们做了「Counterpoint」。它专门跟你作对。"

### 演示一(30 秒)—— 先笑一下

输入:**"我喜欢甜豆腐脑。"**

输出:三条结构清晰的"咸党"最强论证,每条带出处。

（现场效果:评审笑。**这一步是在证明"这不是挑衅工具,它甚至可以很可爱"。**）

### 演示二(60 秒)—— 展示真本事 ★

输入:**"我坚定认为应该用微服务。"**

输出:
- 一条来自知名工程博客的**最强反驳**,带完整论证链(前提→结论)
- 点"出处" → **浏览器当场跳转到原文**

> "注意,这不是它编的。这是真实存在的一种观点,而且它比大多数人反驳得更严密。"

### 高光(40 秒)—— 观点体检

展示"观点体检"图:
> "看完几十条之后,它告诉了一件事:我在 8 个议题上有立场,**其中 3 个是自相矛盾的**。
>
> 比如我坚持'代码要简洁',同时又坚持'必须写详尽的防御性检查'。**我以为我很坚定,其实我从没想清楚。**"

### 收尾(25 秒)—— 回到方法论

> "你可能会问:你自己有没有立场?
>
> 这就是我们最后做的事——**我们把规则摊开了。** 每一条'为什么判定这是对立观点'都能被检视,用户还能提出异议。
>
> 我们不假装中立。**我们只是保证,你随时能看见我们是怎么想的。**"

## 8. 评审问答预案

**Q:这和普通的"推荐相反内容"有什么区别?**
A:三点。一是它不只推对立,还做**观点体检**,找出你立场里的内部矛盾;二是它推的是**最强的反驳**而非随机言论,带完整论证链;三是它**可审计**,判定规则对用户公开。

**Q:内容从哪来?**(必问)
A:MVP 阶段我们用人工精选 + 校验的语料池(50-100 组高质配对),保证质量和可审性。这不是妥协——**在有限时间内,10 个话题做到丝滑胜过 1000 个话题做到随机。**

**Q:你怎么保证你不是在输出偏见?**
A:我们不保证中立,我们保证**透明**。每条判定都展示依据,用户可以提出异议,规则可被检视。

**Q:话题边界怎么定?**
A:严格限定在有真实对立、且无风险的领域:技术选型、工程方法论、生活偏好。**政治、宗教等议题明确排除。**

**Q:用户会不会觉得被冒犯?**
A:关键在语气设计。我们的文案不是"你错了",而是"**这里有一个很强的反对意见,你要不要看看?**"——尊重,但不退让。

**Q:商业模式?**
A:订阅制,面向关注认知质量的用户;企业版可作为**团队决策辅助**——帮团队看见被忽略的反面意见。

**Q:技术难点?**
A:不在检索,在**论证链的抽取与质量排序**——怎么保证输出的是"有论证的反驳"而不是"情绪垃圾"。

## 10. 为什么这个项目值得做(给自己的备忘)

**浅做**:推点相反内容 → 一次性笑话
**深做**:观点体检 + 最强反对者 + 可审计规则 → **一个能讲出方法论的系统**

差别不在代码量,在**你想让它成为什么**。

而且它有一个别的项目没有的优势:**它自带立场。** 黑客松里最稀缺的不是技术,是一个团队敢于说出"我们认为这件事值得做"。

**我们不是要做更聪明的算法。我们是要做第一个,不讨好你的算法。**
