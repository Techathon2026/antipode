## 0. 一句话说清要做什么

**输入:** 一段文本
**输出:** 这段文本对某个议题,站在哪一边,以及**凭什么这么判断的原文证据**。

```json
{
  "issue_id": "microservices_vs_monolith",
  "target": "microservices",
  "polarity": "con",
  "strength": "strong",
  "confidence": 0.88,
  "evidence_span": "一个下单请求要跨七个服务,排障时间翻了三倍"
}
```

---

## 1. ★ 两个必须一开始就做对的设计

### 设计一:分两步,不要一步做完

| | 一步做完(❌) | 分两步(✅) |
|---|---|---|
| 输出 | 议题 + 立场一起出 | 先议题对齐,再判立场 |
| 议题一致性 | 差(会出现"微服务"/"微服务架构"/"Microservices"三种写法) | 好(强制走清单) |
| 能否聚合 | ❌ 无法按议题分组 | ✅ 能按 issue_id 分组 |
| 能否找反信息 | ❌ 找不到对应的反面 | ✅ 有确定的对立面 |

**为什么必须分两步:** 你需要**按议题分组**,才能把"仓库里所有讲微服务的条目"和"反仓库里讲微服务的反信息"横向对齐。如果议题标签不统一,你连分组都做不到,更别说找反信息。

### 设计二:议题必须从预定义清单里选,不许自创

**这是最重要的一条架构约束。**

```python
ISSUE_TAXONOMY = [
    {"issue_id": "microservices_vs_monolith", "label": "微服务 vs 单体", "domain": "软件架构"},
    {"issue_id": "tdd_necessity",             "label": "测试驱动开发是否必要", "domain": "工程实践"},
    {"issue_id": "monorepo_vs_multirepo",     "label": "单体仓库 vs 多仓库", "domain": "工程实践"},
    {"issue_id": "react_vs_vue",              "label": "React vs Vue", "domain": "前端"},
    {"issue_id": "rest_vs_graphql",           "label": "REST vs GraphQL", "domain": "接口设计"},
]
```

**理由:** 如果让 LLM 自创议题,它会发明出你语料库里根本没有对立面的议题——**你就永远找不到反信息。** 约束到清单内,能保证每个议题都有确定的二元对立结构。

> 💡 **清单怎么定?** 手动列 10-20 个"技术圈有真实争论"的议题即可。这是唯一需要人工的环节,但一次性投入,后面全自动。

## 2. 核心 Prompt(可直接用)

### System Prompt

```
你是立场分析器。给定一段文本和一份议题清单,判断文本对这些议题的立场。

【硬性规则】
1. issue_id 必须来自给定清单,不许自创。如果一个都不匹配,返回空数组。
2. 立场是文本【实际表达】的立场,不是文本作者的自我声明。
3. evidence_span 必须是原文的【精确子串】,一个字都不能改。做不到就降低 confidence。
4. 遇到讽刺、反话、阴阳怪气,按【实际含义】判断,不要按字面意思。
5. 如果文本只是在【引用】或【转述】他人观点而没有自己表态,标为 undetermined。
6. 如果文本对多个议题都有立场,全部输出。
7. 中立地讨论正反两面而不倾向任何一方,标为 neutral。
8. 注意【隐含立场】:没有直说"我支持/反对",但字里行间态度明确的,要判出来。

【polarity 取值】
- pro: 支持 target
- con: 反对 target
- neutral: 中立讨论,不倾向
- undetermined: 仅转述他人观点,作者未表态

【confidence 取值】0 到 1。证据不充分时必须给低分,不要硬编。

只输出 JSON,不要任何其他文字。
```

### Few-shot 示例(覆盖 5 种难例)

**示例 1 — 直接支持(pro)**
```
文本: 我们把单体拆成微服务之后,部署频率从每月一次提升到每天十次,团队可以独立发布,这是巨大的收益。
输出: {"issue_id":"microservices_vs_monolith","target":"microservices","polarity":"pro",
      "strength":"strong","confidence":0.95,
      "evidence_span":"部署频率从每月一次提升到每天十次","reasoning":"明确陈述收益"}
```

**示例 2 — 隐含反对(con)· 难点**
```
文本: 我们去年上了微服务,结果光是链路追踪就搭了三个月,一个下单请求要跨七个服务,排障时间翻了三倍。
输出: {"issue_id":"microservices_vs_monolith","target":"microservices","polarity":"con",
      "strength":"strong","confidence":0.85,
      "evidence_span":"一个下单请求要跨七个服务,排障时间翻了三倍",
      "reasoning":"未直接表态,但罗列的全是负面后果,隐含反对"}
```
> ⚠️ 注意:文本**没有一个字说"我反对"**,但立场非常清楚。这是最关键的一类。

**示例 3 — 讽刺/反话(con)· 难点**
```
文本: 微服务真是太棒了——我们花了两周才让一个健康检查正常工作。
输出: {"issue_id":"microservices_vs_monolith","target":"microservices","polarity":"con",
      "strength":"moderate","confidence":0.75,
      "evidence_span":"花了两周才让一个健康检查正常工作",
      "reasoning":"反语。字面是褒义,实际表达不满"}
```

**示例 4 — 仅转述,未表态(undetermined)· 难点**
```
文本: 关于微服务,Martin Fowler 认为它适合复杂系统,而 Simon Brown 则认为大多数团队并不需要它。
输出: {"issue_id":"microservices_vs_monolith","target":"microservices","polarity":"undetermined",
      "strength":"weak","confidence":0.9,
      "evidence_span":"Martin Fowler 认为它适合复杂系统,而 Simon Brown 则认为大多数团队并不需要它",
      "reasoning":"仅陈述他人观点,作者未表态"}
```
> ⚠️ 这类**必须排除出反仓库流程**。否则你会把"引用"当成"立场",生成一堆错的反信息。

**示例 5 — 中立(neutral)**
```
文本: 微服务和单体各有优劣,选择取决于团队规模和系统复杂度。
输出: {"issue_id":"microservices_vs_monolith","target":"microservices","polarity":"neutral",
      "strength":"weak","confidence":0.8,
      "evidence_span":"各有优劣,选择取决于团队规模和系统复杂度","reasoning":"无倾向"}
```

## 3. ★ 校验闸门(最便宜的防幻觉手段)

**核心思想:** 让模型输出证据原文,然后用**代码**验证这段证据真的存在于原文里。

```python
def normalize(s: str) -> str:
    """去掉所有空白字符,避免因空格/换行导致误判"""
    return "".join(s.split())

def verify_evidence(text: str, span: str) -> bool:
    """证据必须是原文的精确子串"""
    if not span or len(span.strip()) < 4:
        return False
    return normalize(span) in normalize(text)
```

**为什么这一步这么重要:**

| 情况 | 说明 |
|---|---|
| 证据存在 | 说明模型确实基于原文判断,可信 |
| 证据不存在 | **说明模型在编**,直接打回或丢弃 |

**这是一个几乎零成本、但极其有效的幻觉探测器。** 而且答辩时可以讲:"我们让模型必须交出自己的证据,再用代码验证。" —— 这是很硬的技术表达。

**处理策略:**

```python
MAX_RETRY = 2

def extract_with_verification(text: str, taxonomy: list):
    for attempt in range(MAX_RETRY + 1):
        result = call_llm(text, taxonomy)
        valid = [s for s in result["stances"]
                 if verify_evidence(text, s["evidence_span"])]
        if valid:
            return valid
        # 全不通过 → 重试;最后一次仍失败则返回空
    return []
```

## 4. 置信度阈值策略

```python
def gate(stance) -> str:
    if stance["polarity"] == "undetermined":
        return "reject"          # 未表态 → 绝不用于反仓库
    if stance["confidence"] < 0.6:
        return "reject"          # 低置信 → 丢弃
    if stance["confidence"] < 0.8:
        return "review"          # 中置信 → 可用于仓库,不进反仓库
    return "accept"              # 高置信 → 全流程可用
```

**关键原则:反仓库的门槛要比仓库高一档。**

理由:仓库错了只是"推了条不相关的信息",反仓库错了会变成"给用户塞了条莫名其妙的反对意见",**伤害大得多**。

## 5. 五种难例与对策(速查表)

| 难例 | 例子 | 对策 |
|---|---|---|
| **隐含立场** | "上完微服务,排障时间翻三倍" | Prompt 规则 8 + few-shot 示例 2 |
| **讽刺反话** | "微服务真是太棒了——搭了两周健康检查" | Prompt 规则 4 + few-shot 示例 3 |
| **仅转述** | "A 认为…而 B 认为…" | 标为 `undetermined`,强制排除 |
| **多重立场** | 一篇文章分别评价三种架构 | 输出数组,每个议题一条 |
| **对比式** | "相比 X,Y 更好" | 对 X 判 con、对 Y 判 pro,输出两条 |

## 6. 长文本怎么处理

超过模型上下文的长文(GitHub issue 里的长讨论、论文全文):

```python
def extract_long(text: str, taxonomy: list, chunk_size=3000, overlap=200):
    chunks = split_with_overlap(text, chunk_size, overlap)
    all_stances = []
    for c in chunks:
        all_stances += extract_with_verification(c, taxonomy)
    return merge_stances(all_stances)   # 同议题多条 → 取置信度最高的一条
```

**注意 overlap(重叠),** 否则立场可能正好被切在分片边界上,两边都抽不出来。

## 7. 性能与成本控制

| 技术 | 做法 |
|---|---|
| **缓存** | 按 `hash(text + taxonomy版本)` 缓存结果,重复内容不重复调用 |
| **批量** | 短文本合并成一个请求(注意别超过上下文) |
| **温度** | 抽取任务用 `temperature=0`,保证可复现 |
| **模型分级** | 短文本用小模型,长文本用大模型 |
| **自洽性校验** | 关键条目跑 3 次取多数(贵,只用于演示数据) |

```python
import hashlib, json

def cache_key(text, taxonomy_version):
    return hashlib.sha256(f"{text}::{taxonomy_version}".encode()).hexdigest()
```

> **温度必须设 0。** 立场抽取是判断任务,不是创作任务,随机性只会带来不确定性。

## 8. 怎么验证它准不准(别跳过)

**必须建一个小评测集。** 不用多,50-100 条就够。

```jsonl
{"text": "我们去年上了微服务,排障时间翻了三倍。", "expected_polarity": "con", "expected_issue": "microservices_vs_monolith"}
{"text": "微服务真是太棒了——搭了两周健康检查。", "expected_polarity": "con", "expected_issue": "microservices_vs_monolith"}
{"text": "A 认为适合复杂系统,B 认为大多数团队不需要。", "expected_polarity": "undetermined", "expected_issue": "microservices_vs_monolith"}
```

**要测三个指标:**

| 指标 | 说明 | 目标 |
|---|---|---|
| **立场准确率** | polarity 判对的比例 | > 80% |
| **证据校验通过率** | 证据真的在原文里的比例 | **> 95%** |
| **议题对齐准确率** | issue_id 选对的比例 | > 90% |

> **第二个指标最重要。** 通过率低于 95% 说明模型在编证据,必须回去改 prompt。它是幻觉的早期预警。

## 9. 实施步骤(按顺序做,别跳)

1. **定议题清单** —— 列 10-20 个议题,存成 JSON
2. **写 System Prompt** —— 用第 2 节的,先不加 few-shot,跑 5 条看效果
3. **加 few-shot** —— 把 5 种难例都塞进去
4. **加证据校验** —— 代码实现 `verify_evidence`
5. **建评测集** —— 手写 50 条,跑一遍看三个指标
6. **调阈值** —— 定 accept / review / reject 的分界
7. **接长文本处理** —— 分块 + 重叠 + 合并
8. **加缓存** —— 避免重复调用

**前 5 步做完(约半天到一天),这一环就算通了。**

## 10. 三个最容易踩的坑

### 坑一:让模型自创议题
→ 结果:找到的议题没有对立面,反仓库建不起来。
**对策:强制走清单。**

### 坑二:把"引用"当成"立场"
→ 结果:给用户生成一堆错的反信息。
**对策:`undetermined` 必须排除出反仓库流程。**

### 坑三:不做证据校验
→ 结果:模型编了证据你也不知道,上线才发现质量崩了。
**对策:代码验证子串。这是零成本的保险。**
