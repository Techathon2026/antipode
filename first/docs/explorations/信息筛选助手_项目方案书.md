# 信息考古学家 — 黑客松项目方案书 v2

> 项目代号:**Archaeologist**(信息考古学家)

---

## 0. 电梯陈述(三个版本,按场合用)

**30 秒版(电梯里):**
> 我们的产品叫「信息考古学家」。你的重要信息散落在邮箱、群聊、论坛、GitHub 里,像埋在地下的文物。它替你把这些信息挖出来,筛出你真正关心的,给你一份省流版——而且每一条结论都留着一条线索,让你能一秒回到原文现场。

**10 秒版(评委路过):**
> 它不帮你读得更多,它帮你**只读该读的**,而且每条结论都能**跳回原文验证**。

**一句话内核:**
> 别人帮你读,我们帮你读 + 让你随时查证。

## 1. 叙事重写:为什么是「考古」

### 1.1 改版前的讲法(正确但平庸)

> "信息散落在邮箱、论坛、群聊、GitHub,用户难以聚合,我们做一个跨源信息筛选助手。"

这句话没错,但它是**产品说明书**,不是**故事**。评委一天听 30 遍类似的话。

### 1.2 改版后的讲法(同一个产品,不同的记忆点)

> "你有没有想过——你真正重要的信息,不在你每天刷的地方,而是**埋在你从没打开过的角落**里。三年前的一封邮件、一个群里的第 400 条消息、某个仓库的一条 issue……它们像文物一样埋着。
>
> **信息不该被埋没,它只是缺一个考古学家。**"

### 1.3 同一个功能,两种标签

| 功能(技术不变) | 平庸标签 | 考古学标签 |
|---|---|---|
| 跨源采集 | 多源聚合 | **发掘**:挖开信息的地层 |
| 相关度筛选 | 智能过滤 | **鉴定**:哪些才是真文物 |
| 分级摘要 | AI 摘要 | **修复**:把碎片还原成完整故事 |
| **原文深链接** | 溯源链接 | **回现场**:带你去看它出土的位置 |
| 主题聚合 / 3D 星图 | 数据可视化 | **时间轴 / 星图**:看见你的信息地质层 |

> 注意:**功能一个都没加,一个都没改。** 改的只是你怎么称呼它、怎么讲它。

## 2. 项目定位与差异化

### 2.1 真实痛点

信息散落在邮箱、论坛、群聊、GitHub,用户面临的不是"搜不到",而是:

- **挖不出来** —— 信息散在多处,没有统一的入口
- **挖出来也读不完** —— 量大、重复度高
- **读了也不敢信** —— AI 摘要不知道从哪来,无法验证

### 2.2 差异化(评审必问:你和 Notion AI / Readwise 有什么区别?)

| 维度 | 现有工具 | 本项目 |
|---|---|---|
| 覆盖范围 | 单一平台 | **跨源聚合**(任一源可接) |
| 交互方式 | 浏览式 / 手动订阅 | **自然语言下指令** |
| 信任问题 | 只给摘要 | **摘要 + 原文深链接(秒级验证)** |
| 情感属性 | 效率工具 | **"找回被埋没的信息"的叙事** |

> ⚠️ **Demo 的高光时刻 = "回现场"这个动作。** 摘要讲完,当场点链接,浏览器瞬间跳到那条 issue。这一下必须丝滑,这是整个演示的记忆点。

### 2.3 黑客松 MVP 边界

**只做 1 个源:GitHub。** 理由:API 干净、PAT 授权简单、数据有结构、技术评审认可度高。

**MVP 必须包含(缺一不可):**

1. 自然语言输入框 —— 用户说"我关注某方向,把这周相关的筛出来"
2. 意图解析 —— 自然语言 → 检索参数(关键词 / 时间窗 / 类型)
3. GitHub 采集 —— star 仓库的 issue / PR / release / commit
4. 相关度筛选 + 分级摘要 —— 输出省流卡片
5. **"回现场"深链接** —— 每条卡片一键打开对应 GitHub 页面
6. 授权面板 —— 用户看到并确认读取范围

**彩蛋(时间够才做,按优先级):**

- 主题聚合视图(散落条目 → 3-5 个主题)
- **3D 信息星图**(见第 7 节,视觉杀手锏)
- 第二数据源(邮箱,证明"跨源"是真的)

**明确不做(写进方案,体现克制):**

- 完整多账号 OAuth 体系(用 PAT 或预授权演示账号)
- 移动端 / 实时推送

## 3. 系统架构

### 3.1 分层架构

```
① 交互层   自然语言指令 + 授权确认面板
                  ↓
② 发掘层   GitHub Connector (MVP) → 统一文档 Schema
                  ↓
③ 鉴定层   清洗 → 去重 → 相关度打分 → LLM 摘要
                  ↓
④ 交付层   省流卡片 + 「回现场」深链接 (+ 主题聚合 / 3D 星图)
```

### 3.2 关键设计:统一文档 Schema(考古学的"文物档案卡")

**这是让"跨源"成立的技术前提。** 每个 connector 的输出都必须转成同一个结构:

```json
{
  "source": "github",
  "source_id": "owner/repo#123",
  "title": "Issue 标题",
  "content": "正文或摘要片段",
  "url": "https://github.com/owner/repo/issues/123",
  "author": "username",
  "timestamp": "2026-10-10T08:00:00Z",
  "type": "issue | pr | release | commit",
  "raw_ref": { "repo": "owner/repo", "number": 123 }
}
```

> 以后加邮箱、论坛、群消息,只需写一个新 connector + 映射函数,鉴定层和前端**完全不用改**。答辩时这句体现架构思维。

### 3.3 意图解析示例

输入:`"我最近在看 RAG 相关的,帮我筛一下我 star 的仓库这周有什么动静"`

```json
{
  "keywords": ["RAG", "retrieval augmented generation", "vector search"],
  "scope": { "source": "github", "repos": "starred" },
  "time_window": "7d",
  "actions": ["issue", "pr", "release", "commit"],
  "output": { "style": "briefing", "group_by": "topic" }
}
```

## 4. 技术选型

| 层 | 选型 | 理由 |
|---|---|---|
| 前端 | Next.js (App Router) + Tailwind | 出活快,卡片式 UI 好写 |
| 后端 | Next.js Route Handlers(FastAPI 备选) | 单仓部署最省事 |
| 采集 | GitHub REST API v3 / Octokit | 官方 SDK,文档全 |
| 检索打分 | 关键词匹配 + embedding 余弦相似度 | 先关键词,有余力上向量 |
| 摘要 | OpenAI API(ChatGPT 那条线) | 手头已有 |
| 存储 | SQLite / 内存 + 缓存 | 别搞数据库集群 |

> **模型使用原则(重要):不要把整个产品做成一个大 prompt。**
> 检索用**代码**做(便宜、快、可控),只把**筛选后的候选**丢给模型摘要。省钱、稳定,还是答辩加分点。

**第 18-30 小时 —— 集成联调**

**第 30-40 小时 —— Demo 打磨(别省!)**

## 6. Demo 脚本(3 分钟版 · 叙事型)

### 开场(25 秒)—— 用故事抓住注意力

> "我有个问题想先问大家:**你上一次从邮箱里翻出一条'要是早点看到就好了'的信息,是什么时候?**
>
> 我们每天被几千条信息淹没,但真正重要的那几条,往往埋在我们从没打开过的角落。**不是因为它们不重要,而是没人帮我们挖。**
>
> 我们做了「信息考古学家」。"

### 演示(90 秒)—— 现场输入

输入:
> "帮我看看我 star 的仓库这周有什么关于 RAG 的动静"

展示:摘要卡片流出 → 聚成几个主题 → **点某张卡片的"回现场"链接 → 浏览器当场跳到那条 GitHub issue**

（讲解话术:"注意,这不是它编的,这是它挖出来的原文——你可以自己看。")

### 高光(30 秒)—— 3D 星图(如有)

旋转视角,展示几十条信息聚成几团"信息星云"。
> "这是你的信息宇宙。每一颗星是它挖出来的一条信息,靠得近的,是同一个主题。"

### 收尾(35 秒)—— 从故事回到技术

> "今天它挖的是 GitHub,但发掘层是插拔式的——加一个邮箱,只需要写一个 connector。
>
> **我们要做的不是又一个摘要工具。我们要让每一条被埋没的信息,都有机会被重新看见。**"

## 7. 视觉杀手锏:3D 信息星图(可选,时间充裕才做)

**用途:** 把聚合后的主题/概念关系渲染成可旋转 3D 星图,作为"信息整合"的展示层。

**映射规则:**
- 每颗星 = 一条信息
- 亮度 = 相关度
- 距离 = 时间远近
- 连线 = 同一主题
- 星团 = 一个主题簇

**为什么值得做:** 视觉记忆点极强,Demo 收尾的冲击力来源。评委没见过会掏手机拍照。

**风险控制:** 只做**静态可旋转**版本,别做复杂交互。时间不够果断砍掉,别为它牺牲主线。

## 8. 评审问答预案

**Q:这和现有的 AI 摘要工具区别在哪?**
A:两点。一是跨源,发掘层插拔式,不锁定平台;二是可验证,每条结论都带原文深链接,解决了摘要"不敢信"的根本问题。

**Q:为什么只做一个数据源?**
A:时间有限,我们选择把一个源做到丝滑可用,而不是四个源都半成品。架构上跨源是现成的,加源成本很低。

**Q:数据隐私怎么办?**
A:授权面板明确展示读取范围,用户主动确认后才开始;数据本地/自托管处理,不做第三方留存。

**Q:"考古学家"是不是只是包装,本质还是筛选工具?**
A:（**准备好这个答案,评委可能犀利**）是的,内核是筛选。但"考古"不是噱头,它精确描述了我们的产品哲学——**信息不是没价值,是没被发掘**。这个定位决定了我们和"帮你读得更多"的工具本质不同:我们追求的是**少而准,且可追溯**。

**Q:商业模式?**
A:订阅制,面向信息过载的知识工作者/研究者/开发者;企业版可对接内部知识库。

**Q:技术难点?**
A:不在接 API,而在跨源归一化 schema 和"相关度打分"的准确性——怎么在有限预算下只把真正相关的丢给模型。
