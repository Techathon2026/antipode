# 接口契约：仓库 → 反仓库

> 这份文档只有一个目的：**让仓库侧（队友）和反仓库侧（我）可以并行开发，谁都不用等谁。**
>
> 两边唯一的耦合就是下面这一个 JSON。契约定下来之后，仓库侧不用管反引擎怎么实现，
> 反引擎也不用管数据是从 GitHub 还是邮件来的。

---

## 1. 边界在哪里

```
队友（仓库侧）                          我（反仓库侧）
接源 → 筛选 → 省流 → 存库   ──库条目 JSON──▶  抽立场 → 检索相反内容 → 省流 → 存反库
```

- **我的输入**：一条「库条目」（VaultItem）
- **我的输出**：零条到若干条「反库条目」（AntipodeItem）
- 我的模块**不负责**采集、不负责兴趣筛选、不负责写仓库 —— 那些都是队友的
- 我的模块**只负责**：判断这条信息站在哪一方 → 找它的对面 → 确认对面确实是它 → 省流写进反库

---

## 2. 输入：库（Vault）与库条目（VaultItem）

### 2.0 第一层：库（Vault）

> **反推荐是按"库"开启的可选能力，不是默认行为**（2026-10-16 定）。
> 所以接口的第一层对象不是"条目"，而是"库"。

示例文件：[`code/vault.example.json`](../code/vault.example.json)

| 字段 | 类型 | 是否必填 | 说明 |
|---|---|---|---|
| `vault_id` | string | ✅ | 库 id，如 `tech-ethics` |
| `topic` | string | ✅ | 兴趣标签名，如"科技伦理" |
| `antipode_enabled` | bool | ✅ | **本库是否开启反推荐** |
| `counter_types` | string[] | 选填 | 要哪几类"相反"，默认只做 `opposing_view`（A 观点对立） |
| `item_count` | int | 选填 | 条目数，用于估算成本与耗时 |

**设计原则：反推荐是用户的选择，不是默认行为。**

| 库的类型 | 是否该开 | 为什么 |
|---|---|---|
| 观点性/争论性兴趣标签（科技伦理、架构选型、工程文化…） | ✅ 开 | 本来就有两派在吵，反信息有价值 |
| 邮件类（订单、通知、工作往来） | ❌ 不开 | **私人事务没有"反面观点"可言**，硬塞会冒犯 |
| 代码仓库 issue 类 | ❌ 不开 | 那是**工作材料**，不是观点表达 |

> 答辩可用的一句话：**"我们不强行挑战你，我们只在你允许的地方挑战你。"**
> 反推荐最大的风险是"像杠精、招人烦"，而"由用户决定开不开"正好化解它。

### 2.1 第二层：库条目（VaultItem）

示例文件：[`code/vault_item.example.json`](../code/vault_item.example.json)

#### 字段表

| 字段 | 类型 | 是否必填 | 说明 | 缺失时我怎么办 |
|---|---|---|---|---|

| `url` | string | ✅ 必填 | **回现场链接** | 没有链接的条目直接丢弃（铁律） |

| `source` | string | ✅ 必填 | `github` / `mail` / `rss` / … | —— |
| `title` | string | 建议 | 标题 | 用 `summary` 前 40 字顶替 |
| `issue_id` | string | 选填 | 议题 id（取 `stance_extractor.py` 里那 16 个议题之一） | **我自己抽** |
| `supports` | string | 选填 | 站在议题的哪一方 | **我自己抽** |

| `tags` | string[] | 选填 | 关键词 | 不使用（我用议题，不用标签） |
| `source_type` | string | 选填 | `issue` / `pr` / `discussion` / `commit` / `note` | 展示用 |
| `lang` | string | 选填 | `zh` / `en` | 展示用 |

### 2.2 ★ 省流版与原版的分工（本节最重要）

抽取器要输出两个东西，而两者的**信息需求完全不同**：

| 输出 | 需要知道什么 | 用哪个字段 | 为什么 |
|---|---|---|---|
| `issue_id`（属于哪场争论） | "**话题是什么**" | `summary` | 省流版足够，且便宜 |
| `supports`（作者站哪一方） | "**作者的态度**" | `full_text` → 切段 <br> 兜底 `raw_excerpt` | **只有原文有态度** |

**为什么省流版不能用来判立场**：AI 概括的目标是"客观复述"，它会**天然消灭态度**。
原文"一个下单请求要跨七个服务，排障时间翻了三倍"（明确反对微服务），
被概括成"作者分享了迁移的成本考量" —— 读不出站哪一方。

这不是省流版做得不好，而是**目标错配**：省流版是给**人**看的，判立场是**机器**要做的事。

**读取顺序（固定）**：

```
summary      → 定位议题（哪一场争论）+ 卡片展示
full_text    → 切段 → 只留带立场信号的段落 → 判立场 + 取证据
raw_excerpt  → full_text 缺失时的替代判据
```

> 为什么不直接把 `full_text` 整篇丢给模型：实测过一个真实弱点 ——
> **一条多议题长句会让模型串议题**（把 TypeScript 严格模式判成"静态 vs 动态类型"）。
> 整篇原文几千字往往同时讨论好几个议题，直接丢进去会"一次输出多条、其中几条议题归错"，
> 还更贵更慢。中间那步"切段 + 粗筛"用关键词与句式规则即可完成，**不需要模型**。

### 2.3 接口是可降级的

**最低可用组合：`id` + `url` + `summary` + 一个原文来源（`full_text` 或 `raw_excerpt`）。**

`issue_id` 和 `supports` 是**可选加速字段**：
- 仓库侧顺手打了这两个标签 → 我直接用，省一次模型调用
- 没打 → 我自己用 3.3 抽取，不阻塞

这个设计的意义：**队友不需要为了我改他们的数据结构。** 契约的必填项恰好都是他们本来就会产出的东西。

**再兜底一层**：如果连 `raw_excerpt` 都没有，我可以拿 `url` 自己去抓原文 ——
所以这件事最坏情况只是多花一点抓取成本，不会让链路断掉。

### 2.4 请队友保住的一个字段

`summary` 我们照用（定位议题够用了），但**请务必同时保留原版**（`full_text` 全文，
或至少 `raw_excerpt` 200–500 字）。理由见 §2.2 —— 这是判断立场唯一可靠的依据，
而原文本来就在队友手上，多存一段文字的成本几乎为零。

## 3. 输出：反库条目（AntipodeItem）

> **存放位置已定（2026-10-16）**：反库存放在**独立的新库**里，不与仓库条目混在一起。
> 仓库与反仓库是两个物理隔离的集合，靠 `for_vault_item` 这一个字段建立对应关系。
> 具体载体（独立 JSON 文件 / 独立表 / 独立集合）由实现阶段定，**接口字段不受影响**。
>
> 为什么坚持物理隔离：产品的整个卖点是"仓库之外还有一层你没看见的东西"。
> 如果反信息混在仓库列表里，这个卖点在演示上就没了 —— 它们必须是两个可以被并排对比的容器。

示例文件：[`code/antipode_item.example.json`](../code/antipode_item.example.json)

| 字段 | 类型 | 是否必填 | 说明 |
|---|---|---|---|
| `id` | string | ✅ | 形如 `anti-<原条目 id>-<序号>` |
| `for_vault_item` | string | ✅ | 回指来源库条目的 `id` —— 反库与仓库的**镜像关系**靠它建立 |
| `issue_id` | string | ✅ | 继承自原条目，或我重抽 |
| `takes_side` | string | ✅ | **它**站在哪一方（必须等于原条目的对立面，见 §4） |
| `counter_type` | enum | ✅ | `opposing_view`（A 观点对立）/ `counter_evidence`（B 反向证据）/ `blind_spot`（C 视野缺失） |
| `url` | string | ✅ | 回现场链接，必填 |
| `title` | string | 建议 | 标题 |
| `summary` | string | ✅ | 省流版 |
| `raw_excerpt` | string | 建议 | 原文片段 |
| `evidence_span` | string | ✅ | 支撑"它站对立面"的**原文子串**，须通过归一化子串校验 |
| `opposition_score` | float | ✅ | 对立度 0–1 |
| `argument_score` | float \| null | P3 再做 | 论证质量分；现阶段写 `null` |
| `gate` | object | ✅ | `{accepted: bool, checked: [...]}` —— 过闸门的凭据 |
| `found_by` | object | 建议 | `{source, query, candidate_id, retrieved_at}` —— 让检索**可复现**，答辩时有用 |

## 4. 铁律：两条，别让步

### 4.1 对立面不是"感觉相反"，是符号运算

```
对立的充要条件：  takes_side == opposite(原条目.supports)
                且  takes_side != 原条目.supports
```

原条目 `supports = "微服务"` → 反库条目的 `takes_side` 必须是 `"单体"`。**没有例外，没有"大致相反"。**

### 4.2 没有可验证证据的，一律丢弃

`evidence_span` 必须是该条目原文的真实子串（归一化后比对，连中英文标点一起去掉）。
拿不出原文子串的候选 → `gate.accepted = false` → 不写反库。

这和 3.3 里那道证据闸门是**同一个判据**。

## 5. 现阶段（P0）只做哪一条路

- `counter_type` **只做 `opposing_view`**（A 类：观点对立）。用来跑通链路，不追求聪明。
- `counter_evidence`（B 类）是演示亮点，放 P3。
- `blind_spot`（C 类）留字段位，人工预置 1 个例子即可。

先跑通"A 类一条"，再谈算法。
