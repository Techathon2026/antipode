## 模块 2：立场段落粗筛（已完成，2026-10-16）

代码 `code/passage_selector.py`。**纯规则、零模型调用、零网络请求。**

### 2.1 它解决什么问题

| 问题 | 不解决的后果 |
|---|---|
| 整篇原文几千字不能直接丢给模型 | 多议题长文会**串议题**（实测把 TS 严格模式判成静态 vs 动态类型）；更贵更慢 |
| 候选侧只有一百字（V2EX/HN 片段） | 切段等于丢上下文，纯属添乱 |

### 2.2 机制

**自适应切段（三级退化）**，因为真实原文排版千奇百怪：

1. 按空行切（Markdown / 博客最常见）
2. 段落数 <3 → 说明没有空行，改按单换行切
3. 单段 >900 字 → 按句子贪心打包成 ≤600 字的块

**短文本快速通道**：全文 ≤400 字直接整段返回，不切分。

**信号打分**（这是核心）：

| 档位 | 含义 | 入选要求 |
|---|---|---|
| 强信号 | 作者明确在下判断（我认为/其实/反而/后悔/代价），或第一手经验（我们公司/后来我们） | 命中 **1** 次即可 |
| 弱信号 | 因果转折与成本类词汇（因为/但是/成本/排障/迁移） | 需命中 **≥2** 次 |
| 反向信号 | 整段只是提问，且无强信号 | **扣分**（提问不是立场） |
| 程序性惩罚 | 配置/部署/参数/示例/集群等技术说明类词 ≥2 个且无强信号 | **不入选** |

**为什么弱信号要 ≥2、还要排程序性段落**：这两条都是自检抓出来的。
一段 Nacos 集群配置说明靠"集群 + 故障"凑够了 2 个弱信号被误召 ——
**技术段落没有立场，但它能凑够词**。这是词袋方法的固有弱点，用惩罚规则压制。

**相邻合并**：连续入选的段落合并成一块（保留上下文，别把论证切成碎片）。

### 2.3 实测数字

内置样例（755 字，10 段，混有 4 段观点 + 4 段技术说明）：

```
原文字数 755  →  选出 271 字（压缩比 36%）
段落 10 → 选中 2 块（其中 1 块由 3 个相邻观点段合并而成）
```

10 项自检全部通过，其中两条是**防止误召**的关键断言：
- ✅ 抓到了「我认为这笔交换不划算」段
- ✅ 抓到了「后来我们把订单和库存合并回去」段
- ✅ 没抓 Nacos 配置说明段
- ✅ 没抓网关/监控技术段

### 2.4 已知局限（要如实说）

1. **词袋方法的固有弱点**：靠信号词计数区分"观点段"和"技术段"，
   遇到新写法（比如通篇不用"我认为"而用叙事暗示态度）仍会漏。
   —— 但这只是**召回层**的偏差，判定权在模型手里，漏一段的代价是少一条候选，不是错一条。
2. **信号词表是人工写的**，中英混排，英文侧比中文侧成熟。
3. **压缩比与文章类型强相关**：观点密集的短文压缩比高（本例 36%），
   通篇讨论的长文压缩比会更高（更省），纯技术文档则可能压不下去。

### 2.5 与其他模块的接口

```python
from passage_selector import select_from_vault_item, select_passages

# 库条目 → 精选段落（自动按 full_text → raw_excerpt → summary 降级，并标记是否降级）
passages, stats = select_from_vault_item(vault_item)

# 任意文本 → 精选段落
passages, stats = select_passages(text, max_passages=12)

# stats 里的关键字段
#   compression     压缩比（省下的就是模型成本）
#   source_field    实际读了哪个字段
#   degraded        是否降级（没读到 full_text）
#   all_passages    逐段判定明细（审计用）
```

## 模块 ④⑤⑥：二次判立场 / 省流 / 写入反库（已完成，2026-10-16）

代码 `code/antipode_engine.py` —— 把模块 0-3 串成端到端流水线。

### 4.1 首次真实端到端结果

```
库条目 gh-issue-482（队友标注：支持「微服务」）
① 判立场       微服务  ← 队友已标注，省一次模型调用
② 取对立面     单体
③ 检索候选     26 条（同源 17 / 全网 9；v2ex 17 / hn 9）
   粗筛送检     8 条
④ 二次判立场   8 次调用 → 通过 5 条（拒因：判不出 3）
   截断         2 条（超出 top-k）
⑤ 省流         3 条（全部为模型生成）
⑥ 写入反库     3 条 → data/antipode_tech-ethics.jsonl
```

产出的三条都是**真实名篇**，URL 直通原文博客：
`Don't start with microservices – monoliths are your friend` /
`Monoliths Are the Future` / `Modules, not microservices`。

### 4.2 ★★ 排序上连踩两个坑（值得写进答辩材料）

| 版本 | 做法 | 后果 |
|---|---|---|
| v1 | 只按对立度排序 | **"第一档 origin"被架空** —— 检索时优先了同源，但 HN 标题本身就是完整立场（置信度 1.0），排序时把同源全压下去，最终三条全来自全局档 |
| v2 | 同源**硬优先级** | 走到另一个极端 —— 把一条对立度只有 **0.60** 的同源候选，排在了两条 **1.00** 的全局候选前面，**质量换来了纯度** |
| v3（采用） | 按质量排序，同源给 **1.25 倍温和加成** | `0.60×1.25=0.75 < 1.00`（压不过真正的强对立）；但 `0.85×1.25=1.06 > 1.00`（够强就能赢） |

**最终理解**：**"第一档"管"去哪儿找"，不管"最终选谁"。**
检索严格按三档；排序仍按质量，同源只给温和加成。

### 4.3 ⚠️ 暴露的瓶颈：内容厚度不够

当前真实数据下三条全来自 HN，原因是 **HN 文章模式只有标题**：
- 标题本身就是一句完整立场（"Monoliths Are the Future"）→ 模型给 1.0 置信度
- 但**证据也只有标题** —— 那是"声明"，不是"论据"
- 省流成了标题的同义改写，摘不出新信息

而 V2EX 候选虽然有正文片段，片段却常是对话题的技术描述而非立场句 → 置信度只有 0.6。

**这是"中文优先"目前达不到的直接原因**，也是下一步要解决的目标：
给 HN story 补正文或取其讨论评论、给 V2EX 候选补帖子正文。

### 4.4 漏斗账目必须准确（另一处修正）

第一版把"通过但因超出 top-k 未输出"的条数漏掉了，导致
`通过 + 拒 ≠ 送检`，漏斗对不上账。已拆成两个独立字段：
`passed`（通过）→ 减去 `truncated`（截断）→ `accepted`（输出）。
自检里加了断言 `accepted + truncated == passed`。

### 4.5 ★ 判定单元（unit）：把"整条候选"拆成"作者真的在表态的最小片段"

第 ④ 步的核心抽象不是"判这条候选算不算对立"，而是**先拆单元、再逐个判**。
因为把一整条候选当整体判，会系统性地判错。三种单元来源：

| 来源 | 何时用 | 为什么 |
|---|---|---|
| **HN 讨论评论** | 候选是 HN 文章（补过评论） | 讨论区天然两派在吵，整段判会得"中立"，而且拿不出"是哪句话" |
| **段落粗筛** | 候选正文 > 800 字（如 CSDN 2000+ 字教程） | ⚠️ 实测逼出来的：CSDN 多是"微服务的优缺点"这种**两面都讲**的教程，整篇判必然得中立 → **18 条候选全军覆没**。切段后只判"作者表态的那段"才对 |
| **整条** | 其余（V2EX 单议题帖，约 571 字） | 内容本身就是单一立场，不必拆 |

这样设计后，**证据天然是"那一句话"**，且 `evidence_url` 能指到证据本身
（HN 评论有永久链接；段落指向帖子）。

### 4.6 ⚠️ 中文评价词与英文不对称（已修）

排查"CSDN 候选一条都进不了最终结果"时发现的：`STANCE_HINTS` 英文侧写了
`why / goodbye / better / overkill / trap`，中文侧却只有 `为什么 / 其实 / 不如 / 踩坑`
—— **"优缺点""对比""复盘""选型""取舍""权衡""该不该""要不要"全都没写**。

后果：CSDN 标题《单体架构的优缺点复盘——何时该用单体、何时拆分》被判成
"没有立场信号"，在粗筛排队时被挤到后面，**根本没机会进模型判定**。

这不只是漏词，而是**对中文源支持不足的系统性表现**。已补齐中文评价词表。

### 4.7 同源优先的真实效果（实测）

| 情况 | 行为 |
|---|---|
| 同源（v2ex）可用候选 ≥ 3 | **不调用第二档** —— CSDN/juejin 完全不参与，结果全来自 v2ex |
| 同源不足 3 条 | 自动补全网（实测 v2ex 16 + csdn 18 = 34 条候选） |

这是设计意图的正常表现：**CSDN 是"同源不够时的补充"，不是默认源**。

### 4.8 当前最好的一次产出（4 条，保留率 25%）

```
③ 检索候选   16 条（全部同源 v2ex）
   粗筛送检   8 条 → 长文切段 1 条
④ 二次判立场 8 次调用 → 通过 5 条
   拒因分布   中立 1 / 只有提问无立场 1 / 站错边 2
   截断       1 条
漏斗收束     16 → 8 → 4（保留 25.0%）
```

四条全部中文、全部同源，其中第一条是**强反向证据**：

| 标题 | 证据 |
|---|---|
| 从微服务走向单体化 | "CEO 觉得微服务部署极其繁琐……要求把十来个微服务合并成一个。" |
| 微服务的缺点 | （帖子标题即立场） |
| 仔细想想，微服务架构相比于单体服务架构来讲优势也没有很大 | 同上 |
| 微服务体系，企业级应用，Java 厚重之痛！ | "Java 厚重之痛！" |

### 4.9 ★ 三道闸门 + 一个已知误判（诚实记录）

第 ④ 步实际是**四道检查**，每一道都是被实测逼出来的：

| 闸门 | 挡的是什么 | 实测依据 |
|---|---|---|
| **对立性表述** | "关于某一方的技术内容"（无任何负面评价或转向） | 《vuejs 什么情况下用》这类描述帖被模型判成"支持 Vue" |
| **对立度阈值**（≥0.7） | 低置信度的弱立场 | 设计文档里"防杠精三道闸门"的第三条，实现时漏了，补上后拦下 0.6 的条目 |
| **观点性复检** | 教程 / 源码解析 / 入门问答 | 单独问一句"A 表达主张 / B 技术介绍"，不复用 stance prompt（改 prompt 会掉准确率） |
| **问句标题规则** | 技术求助帖 | 见 §9.2 |

**仍然漏过的一类（已知局限，如实记录）**：《vue3 源码解析》这类**纯教程帖**。
它的标题很短、正文里也确实含评价词，四道闸门全过，且模型给 0.95 的高置信度。
本轮 6 条产出里有 1 条属于此类。

**为什么不再继续打补丁**：剩下能想到的规则是"要求候选同时提及议题两侧"
（对比性约束），但它会误杀《微服务的缺点》这种**只批评一方**的有效内容 ——
那是个真实的两难，不是能靠再加一条正则解决的问题。

**这个局限怎么用**：演示时主动讲出来更有价值 ——
"我们知道这类边界会错：把'关于某一方的技术内容'误判成'反对另一方'。
我们加了四道闸门压制它，但它没被完全消除。" **知道自己在哪里会错，比假装不会错更可信。**

## 模型接入点（给队友的对接说明）

> **反引擎不训练任何模型。** 全程只调用现成模型 API + 纯规则 + 公开检索接口。
> 原因：① 没有训练数据（41 条 gold_set 是评测集，不是训练集）；
> ② 现成模型零样本已经到 90.2%，训练收益小；
> ③ 现场演示最怕环境问题，API 只要网络通就能跑。

### 哪些环节需要模型

| 环节 | 需要什么能力 | 现在用什么 | 怎么替换 |
|---|---|---|---|
| ① 判立场 | 文本分类（从 16 个议题里选 1 + 判断支持哪一方） | `glm-4-flash-250414` | 改 `.env` 三个变量 |
| ④ 二次判立场 | 同一个分类能力 | 同上，同一个模型 | 同上 |
| ⑤ 省流 | 生成（摘要） | 同上 | 同上 |

其余环节（② 取对立面、③ 检索候选、⑥ 写反库）**不需要任何模型**。

### 怎么把自训模型接进来

**方式 A：模型对外提供 OpenAI 兼容 HTTP 接口（最省事）**

```bash
# code/.env
OPENAI_API_KEY=你的key
OPENAI_BASE_URL=http://你的服务地址/v1
STANCE_MODEL=你的模型名
```

改完用 `node code/check_api_key.js` 一分钟验证连通性。

**方式 B：本地模型文件（队友训完就是一个模型文件）★ 推荐走这条**

模型文件的形式太多（HuggingFace 目录 / `.pt` / `.pkl` / `.onnx` / `.gguf`），
加载方式完全不同，所以**不预置加载逻辑**，改成接收一个三行的调用函数。
推荐让队友做**离线批处理**，因为对演示最安全：

```
队友写个脚本：输入 JSONL（一行一条候选文本）→ 输出 JSONL（一行一条标签）
我在流水线里读这个结果文件
```

**为什么推荐这条**：零加载延迟、现场不会崩、**队友不在场也能演示**。
现场演示时如果每次都要加载权重，会有一两分钟的空白 —— 评委巡场时这是致命的。

标签文件格式（给队友的交付规格）：

```jsonl
{"key": "5ef4a60625f24996", "label": "单体", "prob": 0.91}
{"text": "我们上了微服务之后……", "label": "微服务", "prob": 0.87}
```

- `key` = 候选文本 sha1 的前 16 位（用 `model_adapter.text_key()` 算，文本长时省空间）
- `text` = 原始文本（直白，便于人工核对；与 `key` 二选一）
- 标签怎么映射到本系统的议题与立场 → 填 `code/label_map.example.json`

适配层已实现：`code/model_adapter.py`（三种后端 + 离线自检 + 标签映射）。

**方式 C：只有 embedding 能力**

embedding **不能当判定器**（判定要输出标签，不是向量）。但可以用在**候选排序**上：
用向量相似度衡量"候选与议题的接近程度"，决定送哪几条进模型，从而省调用。

### ⚠️ 分类模型的一个错配（很重要）

本系统的输出是结构化的：`{issue_id, supports, evidence_span, reasoning}`。
其中 **`evidence_span`（原文里支撑判断的那句话）是证据闸门的输入**，
而**分类模型只能给"标签 + 概率"，给不出证据片段**。

所以分类模型的能力边界是：

| 能做 | 不能做 |
|---|---|
| 当**门**：筛掉不沾题的、明确中立的，减少后续模型调用 | 独立完成一次完整抽取（缺 `evidence_span`） |

→ 结论：**分类模型用来预筛，正文与证据仍由生成式模型补。**
除非队友的模型是多任务输出（标签 + 片段），那才能直接替换 ①。

### 队友的标签体系能不能用？看这张表

| 队友模型的标签 | 能不能判立场 | 怎么接 |
|---|---|---|
| **议题 × 立场**（如 `微服务` / `单体`，共 32 类） | ✅ 能 | 直接接 ①④，但证据仍需生成式模型补 |
| **兴趣类别**（如 `架构` / `前端` / `运维`） | ❌ 不能 | 只能用来**路由**（决定用哪个议题去检索） |
| **情感正负**（好评 / 差评） | ❌ 不能 | ⚠️ 最容易踩的坑：**"反对微服务"和"反对单体"都是负向情感**，情感 ≠ 立场 |

对不上的标签，`label_map` 里 `issue_id` 与 `supports` 都留空即可 ——
系统会自动把它当作"判不出立场"丢掉，**不会污染反库**。

### 需要问队友的四个问题（最小清单）

1. 模型文件是什么格式？（HF 目录 / `.pt` / `.pkl` / `.onnx` / `.gguf`）
2. **训练时用到哪些标签？把标签列表发过来** ← 最关键，决定能不能用
3. 输入是什么？（一段文本？有长度上限吗？）
4. 跑推理需要什么环境？（Python 版本、依赖、要不要 GPU）

只要他答"输入一段文本、输出一个标签"，这边半小时就能接上。

### ⚠️ 三点提醒

1. **任务要对得上。** 立场判断的任务定义是"给定 16 个议题，判断这段文本支持哪一方"。
   如果自训模型是做兴趣匹配或摘要的，**硬接进来会更差** —— 不要为了"用上自己的模型"而接。
2. **必须能稳定输出结构化 JSON。** 抽取器要求返回严格 JSON（含 `evidence_span` 字段），
   小模型的 JSON 不稳定会被证据闸门大量拒掉，反而拖低指标。
3. **兜底始终在。** 接不上或不合适时，只要有 API key 就能跑免费档，不阻塞演示。
