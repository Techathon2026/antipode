# 融合信息软件 — 技术清单

> 这份清单回答一个问题:**做这个产品,到底需要哪些技术?**
> 每一项都标了「MVP 必需度」和「真实难度」,避免你在不重要的地方花时间。

---

## 0. 一分钟总览

| 层 | 需要什么 | 难度 | MVP 必需度 |
|---|---|---|---|
| 接入层 | API 调用 + OAuth + 限流处理 | ★★ | 必需 |
| 数据层 | Postgres + pgvector + Schema 设计 | ★ | 必需 |
| **智能层** | Embedding + LLM 结构化输出 + 混合检索 + 打分 | ★★★★ | **必需(核心)** |
| 编排层 | 异步队列 + SSE + 定时任务 | ★★★ | 必需 |
| 交互层 | Next.js + 流式渲染 | ★★ | 必需 |

**难度集中在智能层和编排层。** 这两块是真正要花时间的地方。

---

## 1. 接入层:把数据拿回来

### 1.1 GitHub(首选源)

| 技术 | 说明 | MVP |
|---|---|---|
| GitHub REST API v3 | 基础接口,够用 | ✅ |
| GitHub GraphQL API v4 | 一次请求拿多个字段,省配额 | 进阶 |
| Octokit SDK | 官方 SDK,别自己写 HTTP | ✅ |
| Personal Access Token | 最快授权方式(比 OAuth 快 10 倍) | ✅ |
| OAuth App | 正经授权流程,但要处理回调 | 进阶 |
| 限流处理 | 认证后 5000 请求/小时,要读 `X-RateLimit-*` 响应头 | ✅ |

**要抓什么:** issue、PR、Discussion、release、commit、starred repos

**⚠️ 经验提醒:** **黑客松用 PAT,不要用 OAuth。** OAuth 的回调、state 校验、token 刷新是现场最容易翻车的地方。

### 1.2 邮件

| 技术 | 说明 | MVP |
|---|---|---|
| **IMAP + 应用专用密码** | 直连邮箱,配置简单 | ✅ 推荐 |
| Gmail API + OAuth | 需要 Google Cloud 项目 + 同意屏幕配置 | ❌ 不推荐 |
| 邮件解析 | MIME 解析(附件、HTML 正文) | ✅ |

**⚠️ 严重警告:** Gmail API 需要创建 Google Cloud 项目、配置 OAuth 同意屏幕、可能触发审核。**在 48 小时黑客松里这是纯粹的坑。** 用 IMAP + 应用专用密码,十分钟搞定。

### 1.3 其他源

| 技术 | 说明 | MVP |
|---|---|---|
| RSS / Atom 解析 | `rss-parser` (Node) / `feedparser` (Python) | 进阶,性价比极高 |
| 网页抓取 | Playwright / Cheerio | ❌ 法律风险,不做 |

> 💡 **RSS 是被低估的源。** 技术博客、社区都有 RSS,接入成本极低,内容质量高,而且是**反仓库最好的素材来源**。

## 2. 数据层:存下来

| 技术 | 说明 | MVP |
|---|---|---|
| **Postgres** | 主数据库 | ✅ |
| **pgvector** | Postgres 向量扩展,一个库搞定关系+向量 | ✅ |
| 统一 Schema 设计 | 所有源归一化(见技术方案第 2 节) | ✅ 必需 |
| 对象存储 | 存原文快照(可选) | 可选 |
| Redis | 缓存 + 任务队列后端 | 进阶 |
| 全文检索 | Postgres `tsvector` 足够,别上 Elasticsearch | ✅ |
| 混合检索融合 | RRF (Reciprocal Rank Fusion) 算法 | ✅ |

> 💡 **别单独部署向量数据库。** pgvector 完全够用,少一个服务少一个翻车点。

---

## 3. 智能层:核心价值所在 ★★★★

**这一层决定产品成败,也是你要花最多时间调优的地方。**

### 3.1 向量化与相似度

| 技术 | 说明 | MVP |
|---|---|---|
| Embedding 模型 | OpenAI `text-embedding-3-small`(便宜好用) | ✅ |
| 中文 Embedding | `bge-m3` 或 `text-embedding-3-large` | 视内容语种 |
| 余弦相似度 | 契合度计算基础 | ✅ |
| 分块 (Chunking) | 长文本切片,注意保留上下文 | ✅ |
| 混合检索 | 向量 + BM25 双路,RRF 融合 | ✅ |
| 重排序 (Rerank) | 召回后用 rerank 模型精排 | 进阶 |

**⚠️ 关键提醒:单用向量检索会漏掉精确术语。** 比如用户搜"RRF",向量检索可能返回一堆"排序算法";BM25 能精确命中。**必须混合。**

### 3.2 LLM 结构化输出

| 技术 | 说明 | MVP |
|---|---|---|
| JSON Schema 约束输出 | OpenAI `response_format` / function calling | ✅ |
| Prompt Engineering | few-shot 示例 + 思维链 | ✅ |
| 长文本截断策略 | 超长内容的处理 | ✅ |
| 成本控制 | 只把候选丢给模型,别全量喂 | ✅ |

**⚠️ 这是全项目最重要的一个技术习惯:**

```python
# ❌ 错误:把所有信息丢给模型让它筛
result = llm("这里有 5000 条信息,帮我挑出相关的")

# ✅ 正确:代码先粗筛,只把候选丢给模型
candidates = hybrid_search(query, top_k=30)   # 代码干粗活
result = llm_structured(candidates)           # 模型干精活
```

**既省钱又稳定,答辩时也是加分点。**

### 3.3 立场抽取(难点 1)

| 技术 | 说明 | MVP |
|---|---|---|
| 立场检测 (Stance Detection) | 判断文本对议题的支持/反对 | ✅ |
| 隐式立场识别 | 讽刺、反话、多重立场 | 难点 |
| 置信度门槛 | 低置信度的不进反仓库流程 | ✅ |

**真实难度:★★★★** —— 一个观点不一定直说"我支持 X",可能是隐含的。这是**准确率最难保证的一环**。

**对策:** 只用主立场 + 设置信度阈值 + 人工校验演示用的数据。

### 3.4 论证质量打分(难点 2)

| 技术 | 说明 | MVP |
|---|---|---|
| LLM as Judge | 让模型判断"有没有论证结构" | ✅ |
| 打分 Prompt 设计 | 定义"什么是好论证" | ✅ 关键 |
| 硬性门槛 | 分低于阈值直接丢弃 | ✅ |

**真实难度:★★★★★** —— **全项目最难的一环。**

原因:让 LLM 判断"这段话有没有论证结构"**很不稳定**,同一个输入可能给出不同分数。而且"什么算好论证"本身就难定义。

**对策(重要):**
1. **先用规则兜底** —— 检测"因为/所以/因此/然而"等论证标记词
2. **LLM 只做二次确认** —— 不要全靠它
3. **宁可漏,不可错** —— 阈值设高一点,宁可少推几条

> 答辩时如果有人问"最难的地方在哪",答案就是这里。**主动承认难点比假装没有更可信。**

### 3.5 对立假设生成(核心创新点)

| 技术 | 说明 | MVP |
|---|---|---|
| 反驳方向生成 | LLM 输出"从哪几个角度反驳" | ✅ |
| 检索词生成 | 中英文双组关键词 | ✅ |
| **禁止模型给答案** | 只给方向和检索词 | ✅ 铁律 |

**这是技术含量最高、也最有产品价值的一步。** 关键是 prompt 设计,让模型**克制**——只提问,不回答。

## 4. 编排层:让流程跑起来

| 技术 | 说明 | MVP |
|---|---|---|
| **异步任务队列** | BullMQ (Node) / Celery (Python) | ✅ 必需 |
| SSE (Server-Sent Events) | 流式推送结果到前端 | ✅ |
| 定时任务 | cron / 云函数定时器 | ✅ |
| 任务状态管理 | 排队/运行/完成/失败 | ✅ |
| 重试与幂等 | API 失败重试,避免重复处理 | ✅ |

**⚠️ 这一层最容易被低估。**

采集一个源 + LLM 调 5 次,可能要 30 秒以上。**如果用同步请求,前端必然超时。** 必须:
1. 请求进来 → 立刻返回任务 ID
2. 后台异步跑
3. 前端用 SSE 接收进度

**这是很多黑客松项目在演示时卡住的原因。**

## 9. 建议的学习顺序

如果要学,按这个顺序,**前面的没通就别碰后面的**:

1. **GitHub API + PAT** —— 半天,先把数据拿回来
2. **Postgres + 统一 Schema** —— 半天,把数据存好
3. **Embedding + 余弦相似度** —— 半天,做出"契合度"
4. **LLM 结构化输出** —— 一天,做出"立场抽取"
5. **异步队列 + SSE** —— 一天,让流程不卡
6. **对立假设生成 + 验证** —— 一天,做出"反仓库"
7. **界面** —— 一天,让它好看

**总学习成本约 5-6 天。** 如果只有 48 小时,建议**分工**:A 负责 1-2,B 负责 3-4,C 负责 7,然后一起攻 5-6。

## 10. 诚实总结:最难的三件事

如果让我只提醒三件事:

### ① 立场抽取的准确性(★★★★)
一个观点不一定明说。**这是准确率的瓶颈。** 对策:置信度门槛 + 人工校验演示数据。

### ② 论证质量打分(★★★★★)
让 LLM 判断"有没有论证"很不稳定。**全项目最难。** 对策:规则兜底 + LLM 二次确认 + 阈值设高。

### ③ 异步编排(★★★)
容易被当成"工程细节"忽略,但它决定了 Demo 会不会卡住。**必须一开始就做对。**

**其余部分(GitHub API、pgvector、Embedding、Next.js)都是成熟技术,调库就行,不要在这里花时间。**
