# 融合信息软件 — 技术方案:仓库 + 反仓库

> 项目定位:**根据你的兴趣建一个信息仓库,再根据仓库建一个反仓库。**
> 仓库解决"读不完",反仓库解决"想不到"。

---

## 0. 一句话架构

```
用户兴趣 + 授权信息源 → 仓库(契合度排序) → 反仓库(观点相反) → 用户完整视野
```

**仓库是"我关注的",反仓库是"我没想到的"。**

---

## 1. ★ 先厘清:反仓库的"相反"是三种不同的东西

**这是整个项目最容易做错的判断。** 如果不区分,反仓库一定是杠精池。

| 类型 | 定义 | 例子 | 技术路径 | 价值 |
|---|---|---|---|---|
| **A. 观点对立** | 同议题,反立场 | 你信微服务 → 推"单体更好" | 立场检测 + 反立场检索 | 低(谁都做得出) |
| **B. 反向证据** | 反驳你结论的事实 | 你信"微服务=高可用" → 推"某公司因微服务宕机 12 小时" | 论证结构匹配 | **高** |
| **C. 视野缺失** | 你完全没覆盖的相邻议题 | 你只看"微服务" → 推"Serverless" | 覆盖度缺口分析 | **高** |

### 实施策略

- **MVP 做 A** —— 用来证明链路能跑通
- **演示亮点做 B 或 C** —— 这才是"开拓视野"的真身
- **架构上三个位置一次留出** —— 数据模型里用 `counter_type` 字段区分,否则后面改不动

> ⚠️ 如果反仓库只有 A,产品会退化成"抬杠机"。**B 和 C 才是护城河。**

## 2. 数据模型

### 2.1 统一信息条目(仓库)

所有信息源(GitHub / 邮件 / 论坛)都归一化成这个结构:

```json
{
  "id": "item_001",
  "source": "github",
  "source_id": "owner/repo#123",
  "title": "为什么我们选择微服务架构",
  "content": "正文或摘要片段",
  "url": "https://github.com/owner/repo/issues/123",
  "author": "username",
  "timestamp": "2026-10-10T08:00:00Z",
  "topic": {
    "domain": "软件架构",
    "issue": "微服务 vs 单体"
  },
  "stance": {
    "issue_id": "microservices_vs_monolith",
    "supports": "微服务",
    "side": "a",
    "confidence": 0.86,
    "evidence_span": "支持该立场的原文片段"
  },
  "opposite": "单体",
  "relevance": 0.91,
  "quality": 0.78,
  "collected_at": "2026-10-13T10:00:00Z"
}
```

**关键字段说明:**
- `topic.issue` —— **粒度必须可控**。太粗("技术")无法对立,太细("React 18 useEffect 依赖数组")没有对立面。建议两级:`domain` 粗 + `issue` 细。
- `stance.side` —— `a` / `b` / `neutral` / `undetermined`。**直接标"文本支持清单里的哪一方",不做 pro/con 抽象转换** —— 否则同一句话会有两种合法标法,反仓库无法对齐。详见 `立场抽取_实施指南.md` 的设计一。
- `opposite` —— 反仓库要去找的那一方,由 `side` 派生(`a`→side_b)。`neutral` / `undetermined` **没有对立面**,必须排除出反仓库流程。
- `stance.evidence_span` —— 保留原文证据片段,保证可追溯

### 2.2 反仓库条目

```json
{
  "id": "counter_001",
  "target_item_id": "item_001",
  "counter_type": "opposite_stance | counter_evidence | blind_spot",
  "issue": "微服务 vs 单体",
  "counter_claim": "在中小团队中,微服务带来的运维复杂度超过其收益",
  "argument_chain": [
    "前提 1: 微服务的收益随团队规模增长",
    "前提 2: 中小团队缺乏专职运维",
    "结论: 运维成本超过收益"
  ],
  "source": {
    "url": "https://...",
    "title": "原文标题",
    "author": "...",
    "quote": "支持该论证的原文片段"
  },
  "scores": {
    "opposition": 0.82,
    "argument_quality": 0.75,
    "source_credibility": 0.80
  },
  "verified": true,
  "audit_reason": "判定为对立:立场向量夹角 152°,且直接反驳 target 的核心前提",
  "created_at": "2026-10-13T10:05:00Z"
}
```

**三个字段是信任基础:**
- `source.url` + `source.quote` —— 每条反信息都能一键跳回原文验证
- `audit_reason` —— 展示"我为什么判定它对立" → **可审计**

## 3. ★ 核心算法:反仓库构建五步

**贯穿全流程的一条铁律:**

> **LLM 只负责"提出问题",绝不负责"提供答案"。答案必须来自真实检索结果。**

这是避免幻觉的唯一可靠方式,也是答辩时最该强调的技术原则。

### 步骤 ① 主题 + 立场抽取

```python
def extract_topic_and_stance(item):
    # LLM structured output
    prompt = f"""
    分析以下文本,输出 JSON:
    1. 它在讨论什么议题?(issue_id 必须从给定清单里选,不许自创)
    2. 它支持清单里该议题的哪一方?(supports = side_a 或 side_b 的原文,或 neutral / undetermined)
    3. 支持该立场的原文片段是什么?(必须是原文精确子串)
    文本: {item.content}
    """
    return llm.structured(prompt, schema=TopicStanceSchema)
```

**难点:** 隐含立场、讽刺、一篇文章里多个立场。
**对策:** 只取该文最强的主立场;置信度低于阈值(如 0.6)的条目不进入反仓库流程。

### 步骤 ② 生成对立假设(关键设计)

**这里有一个歧路必须避开。**

- ❌ **错误做法:直接"取反"**
  "喜欢猫"的反面是什么?讨厌猫?还是不该养宠物?**没有唯一答案,取反必然歧义。**

- ✅ **正确做法:生成"反驳方向"**
  让 LLM 输出"要反驳这个结论,可以从哪几个角度切入",以及对应的检索词。

```python
def generate_counter_hypothesis(topic, stance):
    prompt = f"""
    议题: {topic.issue}
    当前立场: 支持「{stance.supports}」 → 需要反驳的方向是「{stance.opposite}」
    请输出:
    1. 要反驳这个立场,有哪些有力的切入角度?(3个)
    2. 每个角度对应的检索关键词(中英文各一组)
    注意: 你只需给出"反驳方向"和"检索词",不要给出反驳内容本身。
    """
    return llm.structured(prompt, schema=CounterHypothesisSchema)
```

**输出示例:**
```json
{
  "counter_directions": [
    "运维复杂度与团队规模的关系",
    "微服务在中小公司的失败案例",
    "单体架构的现代化方案"
  ],
  "search_queries": [
    "microservices overhead small team",
    "微服务 失败 案例 复盘",
    "modular monolith advantages"
  ]
}
```

### 步骤 ③ 检索真实来源

```python
def retrieve_real_counter_content(queries, sources):
    candidates = []
    for q in queries:
        for src in sources:
            candidates += src.search(q, top_k=20)
    return dedupe(candidates)
```

**关键原则:检索结果必须带原文 URL。没有出处的候选直接丢弃。**

**源的选择(重要):**

| 源 | 适合做兴趣信号 | 适合做反仓库来源 | 说明 |
|---|---|---|---|
| GitHub | ✅ | ✅ | issue / Discussion 里有真实技术争论 |
| 论坛 / RSS | ✅ | ✅✅ | 对立观点最密集 |
| 技术博客 | ✅ | ✅✅ | 论证质量高 |
| 论文 | ✅ | ✅ | 反驳性论文质量极高 |
| **邮件** | ✅✅ | ❌ | **私人内容,没有对立面** |

> ⚠️ **一个必须记住的结论:邮件不适合做反仓库来源。**
> 邮件是私人的,不存在"相反邮件"。但它是**最好的兴趣信号源**——你的订阅、你的往来,最能反映你真正关心什么。
> **邮件负责"告诉我们你想要什么",不负责"提供反信息"。** 答辩时这个区分会显得你们想得很清楚。

### 步骤 ④ 验证与质量打分(防杠精化的生死线)

```python
def verify_and_score(candidate, target_stance):
    # 1. 对立度:立场向量夹角
    opposition = stance_similarity(candidate.stance, target_stance)  # 需为负相关
    
    # 2. 论证质量:必须有前提→结论结构
    argument_quality = llm.judge_argument_structure(candidate)  # 0-1
    
    # 3. 来源可信度
    credibility = score_source(candidate.source)
    
    # 4. 硬性门槛
    if argument_quality < 0.5:
        return None   # 无论证结构 → 丢弃(这就是过滤杠精)
    if not candidate.source.url:
        return None   # 无出处 → 丢弃
    
    return {
        "opposition": opposition,
        "argument_quality": argument_quality,
        "source_credibility": credibility,
        "verified": True
    }
```

**三道闸门,缺一不可:**
> 实现阶段按实测又补了三道（教程标题、自指排除、议题覆盖度），当前共六道；
> 口径以 [`反仓库流水线_模块说明.md`](反仓库流水线_模块说明.md) 与答辩看板为准。

1. **必须有论证结构** —— 没有"前提→结论"的,一律丢弃。**这是过滤杠精最有效的一刀。**
2. **必须有可验证出处** —— 没有 URL 的一律丢弃
3. **对立度必须达到阈值** —— 避免"看似对立实则同一个观点"

### 步骤 ⑤ 写入反仓库

- 按 `issue` 聚类(同一议题的反信息归在一起)
- 每议题保留 Top-N(如 3-5 条),按综合分排序
- 保留 `audit_reason`,支持用户查看判定依据

## 4. 契合度与排序

### 4.1 仓库内排序

```python
final_score = w1 * relevance + w2 * recency + w3 * quality

relevance = 0.6 * embedding_similarity(item, user_interest) + 0.4 * keyword_match
recency   = exp(-days_ago / half_life)   # half_life 可配置,默认 30 天
quality   = source_credibility * content_completeness
```

**权重可让用户调:** "我更看重时效" / "我更看重相关度"。这也是一个产品卖点。

### 4.2 反仓库内排序

```python
counter_score = 0.4 * opposition + 0.4 * argument_quality + 0.2 * source_credibility
```

> **注意:反仓库排序里,"对立度"只占 40%,"论证质量"同样占 40%。**
> 这是在用评分机制强制"不要抬杠要讲理"。**答辩时这是个很有说服力的设计细节。**

## 5. 技术选型

| 层 | 选型 | 理由 |
|---|---|---|
| 前端 | Next.js (App Router) + Tailwind | 卡片式 UI 出活快 |
| 后端 | Next.js Route Handlers / FastAPI | 单仓部署最省事 |
| 主题/立场/假设 | LLM structured output | 直接产出 JSON,可控 |
| 检索 | **混合检索:向量 + BM25** | 单用向量会漏掉精确术语 |
| 向量库 | pgvector(跟着 Postgres 走) | 别单独部署向量数据库 |
| 存储 | Postgres + pgvector | 一个库解决关系 + 向量 |
| 调度 | 定时任务(cron / 云函数) | 增量采集 |

**SSE 流式返回:** 前端体验关键。反仓库生成较慢,必须流式出结果,否则用户以为卡死。

## 6. 冷启动问题(一定被问)

**问题:** 仓库为空 → 反仓库无从建起。鸡生蛋。

**解法:**
1. **首次采集即建最小仓库** —— 用户授权后立刻做一次全量拉取,得到 20-50 条初始条目
2. **预设兴趣种子** —— 让用户在授权后勾选几个领域(编程 / 学术 / 商业),快速建立初始兴趣向量
3. **反仓库允许"空态引导"** —— 仓库不足 10 条时,反仓库展示"内容还在积累中",而不是空白或错误

## 7. 分期实施建议(48 小时节奏)

### P0 — 第 1-6 小时:打通一条链路 ★
**目标:硬编码一个议题,从 GitHub 拉回一条信息 → 存进仓库 → 生成一条反信息 → 显示两张卡片。**

- 议题硬编码("微服务 vs 单体")
- 只用一个源(GitHub)
- 反信息可以是**人工预置**的(证明链路,不证明算法)
- ⚠️ **不做任何美化,不做多议题**

**这条链路不通,后面全是空中楼阁。**

### P1 — 第 6-18 小时:让流水线自动跑
- 主题 + 立场抽取(LLM structured output)
- 对立假设生成
- 检索对接第二个真实源(论坛 / RSS)

### P2 — 第 18-30 小时:质量护栏
- 论证质量打分(过滤杠精)
- 对立度计算
- 多议题聚类展示

### P3 — 第 30-40 小时:亮点
- 做 **B(反向证据)** 或 **C(视野缺失)** 中的一种作为演示亮点
- 排名依据可视化、可审计面板

### P4 — 第 40-48 小时:打磨 + 答辩
- Demo 脚本、备用视频、"为什么不做单纯取反"的话术

## 8. ★ 待你决策的三个技术问题

这三个决定会影响后续所有代码,建议现在拍板:

### 决策 1:反仓库内容来源
- **A. 纯检索**(最安全,有幻觉风险=0,但覆盖面受限于能找到的内容)
- **B. 检索 + LLM 改写**(覆盖好,但有幻觉风险)
- **C. LLM 生成 + 检索验证**(推荐起点)

> **我的建议:C。** LLM 生成"反驳方向" → 检索真实内容 → 验证。既保证覆盖,又保证有出处。

### 决策 2:是否允许"视野缺失(C 类)"
C 类最有价值,但需要先能判断"用户缺什么"——这要求覆盖度分析,比 A 类难一个量级。

> **建议:架构留位,演示时只做 1 个精心准备的例子,不追求自动化。**

### 决策 3:反仓库是否强绑定"用户已有观点"
- 绑定:反信息针对性强,但用户必须先有观点
- 不绑定:反仓库可以独立于用户存在,变成"议题的两面"

> **建议:混合。** 有观点时针对性反驳(强);没观点时展示"这个议题的正反两面"(弱但通用)。
