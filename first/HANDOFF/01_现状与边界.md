## 4. 已经拍板的设计决策（不要擅自改）

| 决策 | 内容与理由 |
|---|---|
| **反推荐是可选开关** | 按库存 `antipode_enabled`。邮件、issue、代码仓库**不该开** —— 私人事务和工作材料没有「反面观点」 |
| **反库独立存放** | 不与仓库条目混放，靠 `for_vault_item` 建立对应。卖点就是「仓库之外还有一层」 |
| **三档检索优先级** | ① `origin` 原条目所在的源 → ② `global` 全网 → ③ `synthesized` AI 自编（**默认关闭**） |
| **第三档硬约束** | 绝不编 URL；必须打 `synthesized: true` 并视觉区分；默认关；答辩主动交代 |
| **中文为主** | 检索源只默认中文源（V2EX 主力）。**Hacker News 降为可选** —— 国内没有市场，塞英文硅谷博客是产品错位 |
| **省流 ≠ 立场** | `summary` 只用来定位议题；判立场必须用 `full_text`（省流版会把作者态度抹平） |
| **同形异义用规则拦** | `retrieval_terms.TOPIC_GUARD`（标题优先的两级判断）。**不改 SYSTEM_PROMPT** —— 一改 90.2% 的评测基线就作废 |
| **队友只给 URL** | `vault_fetch.py` 自取正文；抓不到就明确报失败，**绝不编正文** |
| **议题判错先纠偏、后丢弃** | 判出的议题在原文无依据时，先把范围收紧到覆盖率最高那个重判一次，仍不行才标 `off_issue` 丢弃 |
| **条目级 vs 库级分开** | `antipode_eligible`（这条内容适不适合找反面）≠ `antipode_enabled`（这个库用户要不要开）。两级分开界面才不说谎 |
| **不可反推荐的条目也要显示** | 附原因。它们不是失败品 —— 「10 条里只有 1 条值得找反面」本身就是信息 |

## 5. 入口分工（最容易被搞错的地方，实测逼出来的）

| 入口 | 做什么 | 反推荐 | 实测 |
|---|---|---|---|
| GitHub 新项目 | 只做信息收集（README → 省流 → 原文地址） | ❌ 不支持 | 5 条，★ 0，按设计 |
| 知乎**热榜 / 推荐流** | 只做信息收集 | ❌ 基本为 0 | 10 条 → ★ **0 条**：综合时事（票房、欠薪、展馆闭馆）与 16 个技术议题一条都不沾边，闸门 10/10 全拦 |
| 知乎 **`--issue` / `--query`** | 信息收集 + 反推荐 | ✅ | 10 条 → 9 条 ★ → **16 条反信息**，10/10 有产出 |

> **为什么热榜看到 ★=0 是对的**：给一条时政新闻找「技术选型的对立面」本来就无从下手。
> 不是闸门太严，是入口不对。**不要把闸门放松去凑数** —— 那会让整个反库退化成杠精池。

## 6. 数据落盘（文件名规则必须遵守）

每个平台（= 每个库）有固定前缀，前缀必须等于 `platform.id`，否则采集脚本与接口对不上：

```
data/vault_<id>.json          库元信息（topic / antipode_enabled / counts）
data/vault_<id>.items.jsonl   库条目（一行一条）
data/antipode_<id>.jsonl      反库条目（一行一条，靠 for_vault_item 对应）
data/antipode_<id>.stats.json 反引擎体检报告（漏斗、耗时、拒绝原因）
data/vault_<id>.junk.jsonl    被过滤掉的垃圾（带原因）
data/digest_<id>.md           给人看的日报（GitHub 那条线）
data/platforms.json           「我的信息平台」的平台列表（运行时状态，不入库）
```
